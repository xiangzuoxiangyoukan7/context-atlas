# 单知识库、多技术栈设计

## 背景与决策

项目知识库描述的是一个完整项目，而不是某种编程语言。Spring Boot、Python、Vue 等技术可以同时存在于同一项目，并分别服务于不同目录、模块或运行环节。因此初始化只能创建一套 `doc-<项目名>/`，技术栈不得成为知识库分类、模板选择或目录分叉的依据。

本阶段删除 Profile 模型，不提供兼容层。`profiles/`、Profile Schema、Profile 契约、Profile 选择参数和按 Profile 划分的样例全部移除；其中仍有价值的 Java、Python 采集提示合并进通用技术栈采集规则。

## 知识模型

核心模板保留一份“技术栈与工程约定”知识。Agent 根据仓库证据和用户确认，按实际发现记录任意数量的技术项。每项至少描述：

- 技术名称及可确认的版本；
- 使用目录、模块或组件；
- 在项目中的用途；
- 构建、测试和运行命令；
- 配置位置、运行环境与关键约束；
- 信息来源、确认状态和未决项。

技术项不记录占比，也不使用“主要语言”决定知识库行为。未知信息保留为 `missing` 或 Proposal，不由 Agent 猜测。未来增加新技术时，只增加知识内容；核心目录、生命周期、确认协议和验收语义不变。

## 初始化与维护流程

Agent 扫描整个项目后，向初始化模块提交项目根目录、知识库名称和已确认事实。初始化模块固定物化同一套核心模板，并拒绝覆盖已经存在的目标目录。Agent 随后将识别到的技术项写入统一技术栈文档，不要求用户选择 Java、Python 或前端类型。

维护时，新增或删除项目技术都通过普通知识更新协议处理。删除仓库中的某种技术，不会触发知识库切换；Agent 应提出变更 Proposal，经确认后更新当前技术项，并按知识生命周期保留确有审计价值的历史记录。

## 检查与错误处理

检查器只验证统一 Schema、来源、确认、引用、敏感信息和验收追溯，不加载技术栈专属 Schema。无法识别的技术名称是合法知识，不应导致校验失败。缺少版本或命令属于知识缺口；只有结构错误、非法状态、断裂引用、未确认写入或敏感值才是确定性错误。

## 验收设计

黄金样例不再按语言命名或生成四套知识库，改为使用相同结构的两类项目：

1. 单技术项目，用于证明统一模型不依赖技术数量；
2. 多技术项目，同时包含 Spring Boot、Python 和前端技术，用于证明技术共存且不会分裂知识库。

两类样例必须通过同一检查器和目录快照。测试还需证明初始化接口不存在 Profile 参数，仓库不存在旧 Profile 资产，任意技术名称可被记录，已有目标不会被覆盖，反例仍返回精确错误码，并且不会生成 `AGENTS.md` 或 `CLAUDE.md`。

## 清理范围

实施时直接删除 Profile 实现、旧 Profile 文档、按技术栈划分的黄金样例及相关兼容表述。需要保留的采集规则先合并到统一模板和协议中；历史设计文件若不再提供当前决策所需证据，也一并删除。README、知识库功能卡、架构契约、任务包、验收矩阵和实施计划必须只描述本设计。
