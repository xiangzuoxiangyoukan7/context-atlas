# 知识库结构、关系与流转讨论

**日期：** 2026-08-20  
**状态：** 已确认设计  
**来源：** 用户关于关系目录、需求、功能、架构、模块、接口与数据库结构的提问，以及本次对话形成的设计回答  

> 用户于 2026-08-20 明确接受本文第 12 节和第 14 节所列全部推荐方案，批准进入实现。实现结果仍须通过结构检查和实际测试，自动检查不能替代内容确认。

## 1. 总体结论

知识库需要建立以下可追溯主链：

```text
需求 ← 功能 → 模块
          ├→ 接口
          ├→ 数据表
          └→ 验收项 → 验收证据

模块 → 提供接口 / 调用接口
接口 → 读取或写入数据表 / 依赖外部系统
数据表 → 属于数据源
```

各类知识职责如下：

| 类型 | 回答的问题 |
| --- | --- |
| 需求 | 为什么做、要解决什么问题 |
| 功能 | 系统应表现出什么业务行为 |
| 模块 | 哪部分代码负责实现，职责和依赖边界是什么 |
| 接口 | 模块或系统之间如何通信，双方必须遵守什么约定 |
| 数据表 | 数据如何保存以及属于哪个数据源 |
| 验收 | 如何证明需求、功能或接口已经成立 |

这些类型不能仅按目录分类，还必须配套稳定编号、关系方向、状态转换、影响分析和变更后的验证流程。

## 2. 关系目录是否应独立维护

### 问题

关系不应集中写入单独文件。例如订单功能读取订单表，应在订单功能文件中直接关联订单表。系统只需定义规则，然后从具体文件读取关系。

### 回答

该判断正确，但需要区分“关系规则”和“关系实例”。

- **关系规则**定义允许使用的关系、合法起点和终点、方向及影响等级。机器权威应保存在 `.project-kb/schemas/relation-catalog.json`。
- **关系实例**必须写在产生该关系的具体知识文件中，不能集中维护。
- 项目知识库中的 `关系目录.md` 最多保留为简短使用说明，不应保存项目的实际关系清单；也可以在保证知识库仍可独立理解的前提下取消该文件。
- 只手工保存正向关系，反向使用方由检查器计算，避免双向重复维护和漂移。

示例：

```yaml
id: F-ORDER-001
type: feature
title: 创建订单
rel_satisfies:
  - "[[../需求/REQ-ORDER-001-用户提交订单|REQ-ORDER-001]]"
rel_realized_by:
  - "[[../../02-架构与契约/模块/MOD-ORDER-订单模块|MOD-ORDER]]"
rel_exposes:
  - "[[../../02-架构与契约/接口/API-ORDER-001-创建订单|API-ORDER-001]]"
rel_reads:
  - "[[../../02-架构与契约/数据库/DS-BUSINESS/TABLE-PRODUCT-商品表|TABLE-PRODUCT]]"
rel_writes:
  - "[[../../02-架构与契约/数据库/DS-BUSINESS/TABLE-ORDER-订单表|TABLE-ORDER]]"
```

## 3. 需求文档保存位置及需求与功能的关系

### 问题

当前没有清楚说明需求文档存在哪里。一个需求可能由多个功能组合实现，需求文档应关联功能文档。

### 回答

一个需求由多个功能实现是常见情况；一个功能也可能满足多个需求，因此需求与功能是多对多关系。需求应成为独立知识类型，不能与功能混用。

推荐结构：

```text
01-需求与功能/
├─ README.md
├─ 能力地图.md
├─ 需求/
│  └─ REQ-*.md
└─ 功能/
   └─ F-*.md
```

若为了兼容保留现有一级目录名，也可以使用：

```text
01-功能基线/
├─ 需求/
├─ 功能/
└─ 能力地图.md
```

推荐由功能使用 `rel_satisfies` 指向需求，需求侧“由哪些功能满足”通过反向索引计算。该方向能避免需求和功能两边重复更新。

```text
REQ-ORDER-001 用户成功提交订单
├─ F-ORDER-001 创建订单
├─ F-STOCK-001 预占库存
└─ F-PRICE-001 计算订单金额
```

现有 `rel_implements` 容易产生方向歧义，候选方案是改为语义更明确的 `rel_satisfies`；是否修改需评估兼容和迁移成本。

## 4. 技术基线与系统架构是否合并

### 问题

技术基线和系统架构应放在一起，不应维护两个文件。

### 回答

中小项目默认合并是合理方案，但应合并文件而不是取消“技术基线”这一结构化概念。

推荐在 `系统架构.md` 中设置以下章节：

```text
# 系统架构
## 架构概览
## 技术基线
## 系统组件
## 架构关系与数据流
## 关键约束
## 相关模块
```

其中“技术基线”仍记录可验证的技术、版本、用途、目录、构建测试运行命令和配置位置。大型项目内容过多时允许拆成独立 `技术基线.md`。因此规则应是“默认合并、按需拆分、语义一致”，而不是强制所有项目维护两个文件。

## 5. 模块边界、功能和需求如何关联

### 问题

模块边界是否本质上是一种契约；功能和需求如何与模块关联；文件是否按模块命名或存储。

### 回答

模块边界是一种架构契约，规定职责归属、允许依赖和禁止依赖；接口契约则规定边界上的具体通信格式。两者相关但不能等同。

模块建议一模块一文件：

```text
02-架构与契约/模块/
├─ README.md
├─ MOD-ORDER-订单模块.md
├─ MOD-INVENTORY-库存模块.md
└─ MOD-PAYMENT-支付模块.md
```

模块文件记录：

- 职责和明确不负责内容；
- 代码路径或包；
- 允许依赖和禁止依赖；
- 提供及调用的接口；
- 可验证来源和确认状态。

功能通过 `rel_realized_by` 关联一个或多个模块。功能文件不应按模块分目录存放，因为功能属于产品视角，模块属于实现视角；一个功能可能跨多个模块，模块重构也不应迫使大量功能文档移动。

## 6. 内外部接口和其他通信方式如何存储与复用

### 问题

接口契约应覆盖系统自身或外部提供的接口及其他通信方式。这些通信手段如何存储、命名和复用。

### 回答

所有稳定通信约定使用统一的接口知识模型，一项契约一个文件。范围包括 HTTP、RPC、事件、文件、Webhook，以及确有稳定契约价值的模块函数。

推荐平铺存储，通信类型通过字段表达，避免技术形态改变造成文件移动：

```text
02-架构与契约/接口/
├─ README.md
├─ API-ORDER-001-创建订单.md
├─ RPC-STOCK-001-库存预占.md
├─ EVENT-ORDER-001-订单已创建.md
└─ FILE-SETTLEMENT-001-结算文件.md
```

示例元数据：

```yaml
id: API-ORDER-001
type: interface
interface_kind: http
visibility: external
version: v1
rel_provided_by:
  - "[[../模块/MOD-ORDER-订单模块|MOD-ORDER]]"
```

接口正文记录入口、语义、输入、输出、错误、敏感字段、版本及兼容策略。接口只定义一次，所有功能和模块引用同一个稳定 ID。消费者不在接口文件内重复维护，由 `rel_calls`、`rel_exposes` 等正向关系的反向索引计算。

## 7. 数据库结构如何简化

### 问题

当前数据库设计过于繁琐。应按数据源隔离，公共信息放在数据源下的统一文件，每张表单独一个文件，并关联所属数据源。

### 回答

建议默认模型简化为“数据源目录 + 一表一文件”：

```text
02-架构与契约/数据库/
├─ README.md
├─ DS-ORDER-订单数据源/
│  ├─ README.md
│  ├─ TABLE-ORDER-订单表.md
│  └─ TABLE-ORDER-ITEM-订单明细表.md
└─ DS-ANALYTICS-分析数据源/
   ├─ README.md
   └─ TABLE-ORDER-DAILY-订单日报.md
```

数据源 `README.md` 保存数据库产品、版本、用途、配置位置、环境变量名称、访问和安全约束、公共命名及事务规则，不保存密码或密钥。表文件通过 `rel_belongs_to` 关联数据源；目录位置同时提供人类可读的归属。

数据库单元和命名空间不应强制创建。通常可作为数据源元数据中的 `database`、`namespace` 字段；只有复杂拓扑确有独立追踪价值时，才升级为独立知识项。

## 8. 功能和接口如何区分及关联

### 问题

功能和接口能否合并；如果不能，应该按“需求到功能、功能到接口”怎样关联。

### 回答

功能和接口不能合并：

| 对比项 | 功能 | 接口 |
| --- | --- | --- |
| 描述对象 | 用户或业务可感知行为 | 系统边界上的通信约定 |
| 关注点 | 场景、规则、结果、异常 | 输入、输出、错误、版本、兼容 |
| 是否一定存在接口 | 不一定 | 通常服务一个或多个功能 |
| 主要变化来源 | 产品需求 | 通信方式和兼容要求 |

例如“自动取消超时订单”可能没有外部接口；而“查询订单接口”可能同时被用户端、客服、对账系统和管理后台复用。

推荐关系如下：

```text
功能 --rel_satisfies--> 需求
功能 --rel_realized_by--> 模块
功能 --rel_exposes/rel_uses--> 接口
模块 --rel_provides/rel_calls--> 接口
功能/模块/接口 --rel_reads/rel_writes--> 数据表
需求/功能/接口 --rel_verified_by--> 验收项
```

不能强制所有知识都经过完整的“需求 → 功能 → 接口”链，因为并非每个功能都有接口，也并非每个技术接口都直接对应单一业务需求。

## 9. 文件命名候选规则

所有可独立引用的知识使用稳定 ID；ID 批准后不因标题、路径或实现变化而改变。

| 类型 | 文件名候选格式 |
| --- | --- |
| 需求 | `REQ-<领域>-<序号>-<名称>.md` |
| 功能 | `F-<领域>-<序号>-<名称>.md` |
| 模块 | `MOD-<领域>-<名称>.md` |
| HTTP 接口 | `API-<领域>-<序号>-<名称>.md` |
| RPC 接口 | `RPC-<领域>-<序号>-<名称>.md` |
| 事件 | `EVENT-<领域>-<序号>-<名称>.md` |
| 文件契约 | `FILE-<领域>-<序号>-<名称>.md` |
| 数据源 | `DS-<领域>-<名称>/README.md` |
| 数据表 | `TABLE-<领域>-<名称>.md` |
| 验收项 | `AC-<领域>-<序号>-<名称>.md` |

## 10. 端到端流转

1. 收到新需求，创建 `REQ-*` 候选知识，记录来源、范围、约束和未知项，状态保持 `proposed`。
2. 将需求拆成一个或多个 `F-*` 功能；功能用 `rel_satisfies` 指向需求。
3. 功能用 `rel_realized_by` 关联负责实现的模块；模块边界约束职责归属和依赖方向。
4. 存在跨模块或跨系统通信时，创建或复用接口契约；调用方引用接口稳定 ID。
5. 功能、模块或接口通过 `rel_reads`、`rel_writes` 关联实际数据表；数据表关联所属数据源。
6. 需求、功能及必要的接口通过 `rel_verified_by` 关联验收项；验收项再关联实际证据。
7. 知识发生变化时，检查器使用正向关系和反向索引计算直接、间接影响，形成待确认 Proposal。
8. 用户确认后更新相关文件，重新运行结构校验、关系校验和相关验收；检查通过只证明结构和追溯关系有效，不代表业务内容自动获批。

## 12. 实施前需要确认的问题

1. 一级目录使用新的 `01-需求与功能`，还是为兼容保留 `01-功能基线` 并增加子目录。
2. `关系目录.md` 是删除、保留为说明，还是由机器目录自动生成。
3. 是否将 `rel_implements` 迁移为 `rel_satisfies`，以及旧知识的兼容周期。
4. 技术基线采用默认合并、可选拆分，还是仅保留一种物理布局。
5. 功能跨多个模块时是否需要区分主模块和参与模块。
6. 接口类型使用统一 `interface` Schema 加分类字段，还是按 HTTP、RPC、事件、文件分别建立 Schema。
7. 数据库旧四层模型如何迁移到默认两层模型，以及复杂拓扑的升级条件。
8. 新结构涉及的模板、Schema、关系目录、检查器、初始化器、迁移器、黄金样例和发布资产应作为同一变更集同步实施。

## 13. 契约分层、抽离与复用

### 13.1 不按“公共/定制”简单二分

“公共契约”和“定制契约”容易同时指代复用范围、适用范围和存储方式。建议使用以下三个明确层次：

| 层次 | 定义 | 保存位置 |
| --- | --- | --- |
| 契约规则 | 规定合法契约必须具备的字段、状态、版本和关系 | `.project-kb/schemas/`、关系目录及知识治理规则 |
| 独立契约 | 可独立引用、复用、版本化、验收或分析影响的具体契约 | `02-架构与契约/` 下对应的模块、接口、数据库或外部依赖目录 |
| 局部约束 | 仅对当前需求、功能、模块或接口成立，没有独立生命周期的规则 | 对应知识文件正文 |

文件组织的判断依据不是契约被称为“公共”还是“定制”，而是它是否具有独立身份和生命周期。

### 13.2 必须抽成独立契约的条件

满足以下任一条件时，约定应抽成一契约一文件：

- 跨越模块、进程、系统或组织边界；
- 被多个功能、模块或系统复用；
- 具有独立提供方和消费方；
- 具有独立版本或兼容策略；
- 需要单独引用、验收或影响分析；
- 变化会影响多个调用方；
- 即使当前只有一个使用方，也有明确的独立通信或演进生命周期。

例如支付结果 Webhook 即使当前只服务支付功能，仍具有外部提供方、签名验证、重试语义和版本要求，应保存为：

```text
02-架构与契约/接口/WEBHOOK-PAY-001-支付结果通知.md
```

功能文件只通过关系引用，不复制契约正文。

### 13.3 可以保留在具体文件中的局部约束

以下内容可以直接写在对应需求、功能、模块或接口文件中：

- 只服务当前知识项；
- 没有独立版本；
- 不会被其他对象直接引用；
- 不需要单独验收或计算影响；
- 离开当前上下文便没有完整含义。

例如“创建订单单次最多购买 100 件商品”可以写在创建订单功能中；`quantity` 必须大于零可以写在创建订单接口的输入约束中。这些内容分别是功能和接口契约的组成部分，不需要继续拆成微小契约文件。

### 13.4 项目内公共契约与跨项目公共标准

项目内被多个功能或模块复用的契约，保存在当前项目的契约目录，例如统一审计事件或文件导入格式。

跨项目共同遵循的组织标准不应在每个项目复制为可独立漂移的权威副本。当前项目应记录：

- 外部或组织级权威来源；
- 当前采用的标准版本；
- 理解本项目所需的关键约束；
- 本项目的扩展和差异；
- 无法访问权威源时的未知项或风险。

项目本地契约可以使用 `rel_conforms_to` 关联公共标准，但本地扩展不得冒充公共标准本身。

### 13.5 局部约束升级为独立契约

当局部约束后来被多个对象复用，或出现独立版本和兼容要求时，应执行升级：

1. 创建独立契约并分配稳定 ID。
2. 将公共规则及来源迁入独立契约。
3. 原知识文件改为关系引用。
4. 只在原文件中保留该对象特有的差异。
5. 使用替代关系保留必要追溯。
6. 运行关系检查和影响分析。
7. 经确认后更新状态，并重新执行相关验收。

### 13.6 统一判断顺序

```text
是否跨越模块、进程、系统或组织边界？
  是 → 独立契约

是否有独立版本、兼容策略、责任方或验收？
  是 → 独立契约

是否被多个知识项复用或需要单独分析影响？
  是 → 独立契约

以上都不是
  → 写入对应知识文件，作为局部约束
```

因此，本讨论采用以下候选原则：

> 可复用、跨边界或具有独立生命周期的契约，抽离为规定目录下的一契约一文件；只属于某个知识项的局部约束，写在对应 Markdown 文件中。具体文件通过关系引用独立契约，不复制其正文。

## 14. 实施门禁与提交规则

本设计不得从讨论稿直接进入实现。执行顺序固定为：

1. 汇总所有需要项目责任人确认的结构、语义、兼容和迁移问题。
2. 对每个问题给出推荐方案、备选方案和影响。
3. 用户逐项确认，或明确确认包含全部选项的完整 Proposal。
4. 仍有冲突、未知项或未确认问题时不得修改模板、Schema、检查器及发布资产。
5. 全部问题确认后，按功能边界拆分实施和验证。
6. 每个功能形成独立 Git 提交，不把无关修改混入同一提交。
7. Git 提交信息使用中文，并准确描述该提交完成的功能。

## 15. 确认记录

用户于 2026-08-20 对以下十四项推荐方案逐项明确表示接受：

1. 保留 `01-功能基线` 一级目录，在其下新增 `需求/` 与 `功能/`。
2. 保留人类可读的 `关系目录.md`，机器规则以 `relation-catalog.json` 为权威，关系实例写在具体知识文件中。
3. 使用 `功能 --rel_satisfies--> 需求`，为旧 `rel_implements` 提供一个兼容周期和迁移能力。
4. 默认将技术基线合并到 `系统架构.md`，大型项目允许拆分。
5. 模块一项一文件，功能通过关系关联模块，不按模块目录存储功能。
6. 跨模块功能区分主要模块和参与模块。
7. 接口使用统一 Schema 和 `interface_kind` 分类，一契约一文件并在接口目录平铺。
8. 采用契约规则、独立契约、局部约束三级模型。
9. 项目内公共契约保存在项目契约目录；跨项目标准记录来源、版本和本地差异。
10. 数据库默认简化为数据源目录加一表一文件，复杂层级按需启用。
11. 只保存正向关系，反向关系由检查器计算。
12. 需求、功能和接口均可关联验收项，模块和数据表按实际独立验收需要关联。
13. 提供自动迁移和一个版本的旧结构读取兼容，迁移不覆盖未提交内容，未知项保持待确认。
14. 按功能拆分实施和 Git 提交，提交信息使用中文。
