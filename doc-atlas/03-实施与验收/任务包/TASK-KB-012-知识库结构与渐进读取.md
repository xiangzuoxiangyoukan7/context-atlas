# TASK-KB-012：知识库结构、内容路由与渐进读取

## 用户确认的完整目标

建立一套目录职责清晰、初始化内容可由当前代码补齐、空项目不会产生虚构事实、后续可以确定性更新，并能在日常使用中渐进读取的项目知识库。

目标不止是移动固定文件，还必须保证初始化器、更新能力、日常读取规则、Schema、检查器、发布资产和示例对同一套知识归属规则保持一致。

## 已确认的目录职责

| 目录 | 核心问题 | 确认的职责 |
| --- | --- | --- |
| `00-项目总览` | 项目是谁 | 只保存最小项目身份信息：目录入口、项目概述和跨模块术语 |
| `01-功能基线` | 产品提供什么 | 保存能力地图、功能卡、业务范围和功能验收引用 |
| `02-架构与契约` | 当前如何实现 | 保存技术基线、系统架构、模块、接口、数据库、数据资产和外部依赖 |
| `03-实施与验收` | 当前做什么、如何证明 | 保存当前变更、任务上下文、影响分析、验收矩阵和实际证据 |
| `04-决策记录` | 为什么这样选择 | 保存存在备选方案和权衡的 ADR，不替代当前架构描述 |
| `05-知识治理` | 知识怎样维护 | 保存知识采集、确认、路由、渐进读取及可选协作责任规则 |
| `90-历史归档` | 过去是什么 | 只保存已被现行知识替代且仍有审计价值的历史，默认不作为当前事实读取 |

## 已确认的固定文档规则

1. `00-项目总览` 收缩为 `README.md`、`项目概述.md` 和可选内容的 `术语表.md`。
2. 原“项目目标与成功标准”不再作为强制独立文件：长期定位和职责合并到项目概述；功能成功标准进入功能卡和验收矩阵；任务完成标准进入任务包。
3. 原“项目边界”不再强制独立：简单项目的长期职责和明确不负责内容写入项目概述；复杂的系统或模块边界分别进入项目概述或 `02-架构与契约`。
4. 产品能力地图本质是功能索引，属于 `01-功能基线/能力地图.md`；小型项目可以由 `01/README.md` 承担索引职责。
5. 技术栈与版本属于当前技术事实，改为 `02-架构与契约/技术基线.md`。
6. 知识来源首先属于被支撑的知识项，必须在需求、功能、契约、数据或决策文档自身记录；不能要求读取一个全局来源文件后才能理解当前知识。
7. 协作人员不是项目总览的固定内容；项目确有稳定人员编号需求时，使用可选的 `05-知识治理/协作与责任.md`。

## 已确认的初始化行为

### 已有代码的项目

初始化阶段扫描根 README、现有产品文档、依赖与构建清单、源码模块、API 或消息入口、数据库模型与迁移、测试、CI、发布配置和已有 ADR。扫描结果按目录职责进入初始化 Proposal，经用户确认后写入对应固定文档。

代码观察只能证明仓库事实，不能自行证明产品需求、设计原因或业务批准。无法从仓库确定的内容保持 `missing`、`proposed` 或待确认。

### 空项目

只生成完整目录、入口、空表、模板、机器清单、Schema 和检查器。不得创建虚构功能、ADR、任务、验收证据、技术条目或历史记录。模板应说明以后如何更新。

## 已确认的更新与日常使用边界

- `context-atlas-init` 用于首次初始化知识库。
- `context-atlas-update` 是用户明确要求插件重新扫描、同步、维护或迁移知识库时使用的能力，不是日常开发 Skill，也不是开发门禁。
- 日常开发默认只读取知识库，不自动调用更新 Skill，不自动改写正式知识。
- 日常开发发现新知识时可以提示存在候选，但用户没有明确要求记录时不得写入正式知识库或自动创建提案文件。
- Context Atlas 提供知识事实、约束、关系、影响和证据，不决定用户或其他插件能否执行开发任务。

## 已确认的渐进读取目标

日常读取采用分层加载，而不是递归读取整个知识库：

1. 会话入口：项目根 README、知识库根 README、`knowledge-base.yaml` 和最低治理说明。
2. 意图路由：按问题类型读取一个相关目录 README。
3. 目标知识：读取直接相关的功能、契约、ADR、任务或验收项。
4. 关系扩展：根据任务最多默认扩展一跳，例如功能到契约和验收、接口到使用方、数据表到读写方。
5. 历史层：只有用户询问历史、发生冲突、回滚或审计时读取 `90-历史归档`。

需要新增正式的“知识路由与渐进读取协议”，把知识类型、唯一权威目录、初始化策略、更新触发器、读取层级和关系扩展规则定义成机器和 Agent 都能遵循的规则。

## 尚未完成

截至 2026-08-20，以下第 1、3、4、5、6 项已经完成；仅第 2 项“知识路由与渐进读取协议”按用户要求暂缓。任务保持 `in_progress`，不将暂缓范围误报为完成。

### 1. 来源模型内嵌

- 当前 `source.schema.json`、检查器、迁移器、测试夹具和部分黄金样例仍使用独立 `SRC-*` 来源实体。
- 需要设计每个知识项内嵌来源的统一结构，包含来源类型、精确引用、获取或确认时间以及必要状态。
- 需要决定是否仍允许“被大量知识共同引用的公共来源”作为可选优化；它不得成为理解单个知识项的前置条件。
- 需要迁移现有来源引用并保留追溯信息。

### 2. 知识路由与渐进读取协议

- 在 `05-知识治理` 新增正式协议。
- 定义知识类型到目录和模板的唯一映射。
- 定义会话入口、意图路由、一跳关系扩展和历史读取条件。
- 更新知识库根 README、目录 README 和 Agent 协作规则，使其引用同一协议。

### 3. 目录归属的机器校验

- 检查 `knowledge-base.yaml` 中所有 authority 目标真实存在。
- 根据文档类型或稳定编号检查文件是否位于允许目录。
- 拒绝把功能、技术契约、任务、ADR 或当前知识放入错误目录。
- 验证固定入口完整，同时允许明确声明的可选文件不存在。

### 4. 初始化扫描和内容补齐

- 扩展初始化 Proposal；当前只覆盖目标、范围和技术栈，尚不能表达术语、能力、功能、模块、接口、数据库、外部依赖、已有测试和 ADR。
- 建立仓库观察到目标文档的确定性路由。
- 增加“已有代码项目补齐内容”和“空项目只保留骨架”的端到端测试。
- 确保所有来源直接进入对应知识项。

### 5. 显式维护与日常开发边界

- 修订 Skill、根 README、AI 协作规则和主动采集规则中可能把 `context-atlas-update` 或自动提案误解为日常开发流程的表述。
- 保证普通开发不会自动写知识库、不会自动创建提案、不会被知识库阻塞。
- 只有用户明确要求知识库维护、同步或迁移时才进入写入流程。

### 6. 格式迁移和一致性资产

- 本次结构变化需要新的格式兼容与迁移方案，不能只依赖手工移动文件。
- 更新 `compatibility.json`、迁移器、发布资产和自包含检查包。
- 清理黄金样例和夹具中残留的旧来源实体模型。
- 增加旧结构到新结构、已有实质内容冲突、空项目和多技术栈项目的迁移测试。

1. 先完成来源内嵌模型，因为它会影响所有知识类型的 Schema 和模板。
2. 编写“知识路由与渐进读取协议”，确定目录映射和读取触发器。
3. 扩展检查器，实现 authority 存在性和文档目录归属校验。
4. 扩展初始化 Proposal、扫描映射和渲染器。
5. 修订 Skill 与日常开发边界。
6. 最后实现格式迁移、更新黄金样例并运行全量验收。

## 完成条件

- 新初始化的已有代码项目能根据已确认仓库事实填充正确文档。
- 新初始化的空项目只包含无虚构事实的完整骨架。
- 每项知识可在自身文档中读取来源，不依赖全局来源文件。
- 文档类型放错目录、authority 指向不存在文件或旧固定结构残留时检查失败。
- 日常开发只渐进读取，不自动触发更新或知识写入。
- 显式知识库维护能够安全更新、保留历史并通过确定性验证。
- 核心模板、发布资产、自包含检查包、单/多技术栈黄金样例和正式文档保持一致。
