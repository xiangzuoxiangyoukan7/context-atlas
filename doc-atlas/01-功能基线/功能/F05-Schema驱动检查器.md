# F05：Schema 驱动的确定性检查器

## 目标

检查器实际读取 Schema，对知识库结构、状态、修订、领域版本、链接和追溯关系进行确定性校验。

## 包含

- 元数据、枚举、ID 和状态流转。
- 文档链接和跨知识类型引用。
- 技术栈记录的结构与追溯约束。
- 功能、设计、任务、验收和证据闭环。
- 数据库、原型、外部依赖引用。
- `data_asset` Schema 和数据来源类型列表校验。
- 批准来源、内容修订、领域版本、冲突和敏感信息风险。
- 版本概念的单一权威、字段类型、兼容判断边界和新旧字段冲突。
- 三个平台插件清单由同一构建版本源生成且产品版本一致。
- 格式 7 到格式 8 的迁移保持 `project_version`、业务正文、批准状态、来源、稳定 ID 和历史，并覆盖成功、幂等、陈旧确认拒绝和失败回滚。
- 批准状态、生命周期状态和规格就绪度的独立约束。
- 规范性行为与验收场景覆盖、阻塞问题与就绪度一致性。
- `ADDED`、`MODIFIED`、`REMOVED`、`RENAMED` 和 `SUPERSEDED` 变更增量的目标、完整性、迁移与引用约束。
- 需求、功能、技术对象、外部任务引用和验收证据之间的跨文档一致性。
- 重复身份、孤立项、断裂关系、陈旧项、未解决冲突、未验证来源和权威入口缺口的只读健康报告。

## 检查层次

检查器按语法、引用、规格、覆盖和一致性分层报告。机器可确定的问题使用错误；需要业务或架构判断的问题使用 `review_required`，不得由检查器自动批准内容。语义清晰度审查由只读审查能力提供候选结论，确定性检查器只实施可稳定判定的规则。

## 功能设计

### 设计概述

检查器先由 Schema 校验受控元数据，再由确定性规则检查目录归属、唯一分类关系、目录与分类一致性、规格就绪度、功能设计章节、内嵌场景覆盖和证据引用。格式 11 的 Catalog 不登记独立契约或验收契约。

### 处理流程

1. 读取根清单并解析 `format_version` 与自包含 Schema Catalog。
2. 扫描 Markdown Front Matter，校验类型、状态、字段、稳定 ID 和来源。
3. 构建正向关系索引并校验目标身份和允许方向。
4. 对 `ready` 功能检查规范行为、功能设计、技术对象覆盖和内嵌验收场景。
5. 对任务、矩阵和证据检查其引用的场景是否存在。
6. 分别输出确定性错误和需要人工判断的复核项。

格式 12 的需求就绪度只由需求正文完整性和开放阻塞问题决定。`rel_satisfies` 只形成独立覆盖视图；未被功能承接的完整需求可以保持 `ready`，不得产生结构错误或被解释为已实现。

### 异常、边界与降级

- `ready` 功能必须包含设计概述、处理流程或状态变化、异常边界以及技术对象说明。
- 功能声明的 `acceptance` 必须与正文场景编号完全一致。
- 检查成功只证明知识结构合法，不能证明设计正确、实现完成或业务接受。
- 格式 1 至 9 的遗留类型按对应兼容资产读取；格式 10 出现遗留契约类型必须失败。

### 技术对象与影响

Schema 保持机器结构权威，Python 规则只检查无法由轻量 Schema 稳定表达的跨文件与 Markdown 章节约束。设计质量仍由只读 review 能力和项目责任人判断。

### 设计取舍

设计章节采用稳定 Markdown 标题做最低确定性检查，正文合理性不做关键词打分，避免把措辞风格误判为设计正确性。

## 验收场景

- `F05-AC-01`：检查器以 Schema 为唯一结构规则来源，不维护不一致的硬编码副本；兼容判断只读取 `format_version`。
- `F05-AC-02`：有效样例通过，规定的结构、追溯、版本权威冲突和安全反例失败并提供定位信息。
- `F05-AC-03`：检查器能识别功能缺少设计、行为缺少验收覆盖、阻塞问题与就绪度矛盾、非法或不完整 Delta，并区分确定性错误与人工复核项。
- `F05-AC-04`：检查器能验证需求到功能、技术对象、外部任务引用和验收证据的追溯覆盖，且不会把外部任务状态或归档动作当成正式知识批准。
- `F05-AC-05`：健康检查能稳定定位结构问题、版本权威冲突和人工复核项，且运行前后正式知识摘要不变。
- `F05-AC-06`：完整但尚无功能承接的需求可以标记 `ready` 并通过结构检查；覆盖视图报告 `uncovered`，但不把它当成规格缺陷或实现完成。
