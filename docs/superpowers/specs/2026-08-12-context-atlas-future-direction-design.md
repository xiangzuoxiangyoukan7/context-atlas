## 1. 来源与事实边界

### 1.1 用户明确输入

来源 `USR-20260812-001`：2026-08-12 当前会话中的用户陈述。

- 需要明确固定文档的格式及其保证机制。
- 仓库应提供知识新增、读取、修改、删除的规范，以及内容如何编写、读取和更新。
- 文档变化后，需要识别关联文档及其业务影响。
- 知识库版本应跟随目标项目发布版本；项目发版时应封存对应版本的变更记录。
- 功能和接口需要版本控制。
- 复杂业务需求可能跨越多个功能和接口，知识库需要能够表达这种关系。
- 需要覆盖数据库多模式、多数据源、表级文档和原始数据治理。
- 需要规定外部接口数据的存储格式。
- 外部依赖需要记录第三方库提供的功能清单和项目实际使用范围。
- 文档及文档质检必须使用引用。
- 所有知识项关系必须同时形成对目标 Markdown 文件的内部链接，以便 Obsidian 知识图谱展示文件之间的关联。
- 数据库字段必须记录中文含义和允许存值范围，包括枚举、数值范围、格式、空值和默认值规则。
- 子表中的物理或逻辑关联字段必须在子表文档中链接主表文件，并明确子字段与主字段的映射。
- 数据库是被功能、接口和需求引用的基础知识；数据库文件不反向维护引用它的功能和接口，反向关系由检查器和 Obsidian 反向链接计算。
- 需要说明每类文档如何保存、如何使用、何时更新。
- 当前知识库未来不再支持不能适配 Skill 的 Agent。
- 设计应形成文档，后续逐项更新，避免上下文丢失和遗忘关键决策。
- 面向使用者的内容不得假设使用者理解英文术语；用户文档、提示、报告和方案必须使用中文解释。
- Agent 与用户在开发、设计和评审过程中新产生的知识，不能只停留在会话或其他插件的过程文件中；需要明确主动捕获方式、触发时机和自动入库边界。

### 1.2 仓库观察

- 当前产品能力集中在初始化、知识采集与确认、版本追溯、核心模板和确定性检查器五类能力。
- 当前正式知识项已有 ID、状态、版本、来源和替代关系的基础设计。
- 当前 Schema 目录包含通用知识项、功能、任务、验收、来源、数据资产和项目清单等 Schema。
- 当前尚无独立的需求、变更集合、业务规则、接口、事件、数据源、数据库模式、数据表和外部依赖 Schema。
- 当前引用主要承担追溯作用，尚未形成可计算的类型化关系图和影响规则。
- 当前没有项目发布基线和发版封存契约。
- 当前没有完整的知识 CRUD 契约。
- 当前 `doc-atlas/` 缺少 Skill 检查流程要求读取的 `knowledge-base.yaml`，而核心模板和黄金样例包含该文件。
- 当前批准架构仍要求为不支持 Skill 的 Agent 提供通用协议入口，与用户提出的新方向冲突。
- 当前仓库包含 standalone Skill，但没有面向用户的安装、更新、卸载和版本固定方式，也没有插件清单。

### 1.3 设计边界

- 格式、引用、状态、版本和关系完整性可以确定性检查。
- 业务语义是否正确不能由检查器自动批准，仍需要来源、责任人确认和验收证据。
- 影响分析只能输出确定影响和候选影响，不能在没有人工确认时自动修改业务知识。
- 知识库不得保存密码、Token、私钥、未脱敏个人数据或生产原始数据副本。

## 2. 已批准的未来产品定位

Context Atlas 应从“知识库模板和检查器”升级为“面向 Skill Agent 的版本化知识关系规范”。产品由四层组成：

1. **知识模型规范**：定义需求、功能、接口、数据库、数据资产、任务和验收等当前范围内的知识类型。
2. **知识操作协议**：定义每类知识如何新增、读取、修改、废弃、归档、确认和追溯。
3. **关系与影响分析**：通过显式关系识别变更的直接影响、间接影响和待复核范围。
4. **Skill 与确定性检查器**：Skill 引导 Agent 执行协议，检查器验证结构、引用、版本、关系和发布完整性。

内容格式应尽量保持工具无关，但产品入口只保证支持能够安装和执行 Skill 的 Agent。不再为无法适配 Skill 的 Agent 维护等价降级流程。

## 3. 总体知识模型

### 3.1 单例文档与实体文档

知识库文档分为两类：

- **单例文档**：项目目标、项目边界、术语、技术栈、当前状态等每个知识库只有一个当前入口的文档。项目发版产生按版本归档的变更记录，不建立复杂发布清单。
- **实体文档**：需求、功能、接口、事件、表、ADR、变更集、任务、验收项和验收证据等可以重复创建的知识项。

每类文档必须明确：

- 文档用途；
- 主要读者或 Agent；
- 创建时机；
- 更新触发条件；
- 负责人；
- 必填来源；
- 允许的上游和下游关系；
- 生命周期；
- 质检规则。

### 3.2 已批准的一等知识类型

| 类型 | 作用 |
| --- | --- |
| requirement | 表达业务需求、背景、目标和约束 |
| change_set | 聚合一次跨需求、功能、接口、数据和依赖的业务或技术变化 |
| scenario | 表达跨组件的业务场景和流程 |
| business_rule | 表达可独立追溯和版本化的业务规则 |
| interface | 表达 HTTP、RPC 或内部模块接口契约 |
| event | 表达消息、领域事件及其 payload 契约 |
| data_source | 表达数据库、对象存储、消息系统或外部数据源 |
| database_schema | 表达数据源下的 schema、database 或 namespace |
| table | 表达单表结构、用途、治理和血缘 |

外部依赖能力模型已经暂缓，不属于当前新增类型。项目发布不建立独立 `release` 实体，只按项目版本封存一份版本变更记录。

## 4. 固定格式的保证机制

采用四重约束：

1. Markdown 提供人和 Agent 可读的正文。
2. YAML frontmatter 提供 ID、类型、状态、项目版本字段、来源、责任人和关系等机器字段。
3. JSON Schema 约束每种知识类型的必填字段、枚举、格式和关系目标。
4. 模板、检查器和 CI 保证初始化与后续修改持续符合规范。

检查器应验证文件位置、ID 唯一性、必填字段、引用目标、关系类型、生命周期、项目版本字段、替代关系和版本变更记录。业务内容正确性继续由来源、确认人和验收证据负责。

## 5. 知识 CRUD 与生命周期

### 5.1 Create

新知识必须具有稳定 ID、类型、来源、负责人、首次适用项目版本和必要关系。未经明确确认时保持“待确认”（机器状态 `proposed`）。

### 5.2 Read

Agent 应通过根清单、类型目录和关系索引读取当前有效知识，不依赖目录遍历和文件名猜测。读取结果至少能够定位：

- 当前有效状态和最近修改对应的项目版本；
- 来源和确认状态；
- 上游依据；
- 下游消费者；
- 所属项目发布版本；
- 历史替代链。

### 5.3 Update

更新前必须产生 Change Proposal，至少包含变更字段、原因、来源、直接影响、间接影响、待重新验收内容和兼容性判断。

### 5.4 Delete

- 未批准草稿可以物理删除。
- 已批准知识不应静默删除，应进入“已弃用”（`deprecated`）、“已被替代”（`superseded`）或“已归档”（`archived`）。
- 对外接口、功能、表和业务规则应保留稳定 ID、废弃原因和替代目标。

## 6. 引用、关系与影响分析

### 6.1 类型化关系

正文 Markdown 链接用于阅读导航，机器影响分析和 Obsidian 文件图谱共用受控、扁平的关系属性，例如：

```yaml
rel_implements:
  - "[[01-需求/REQ-001-订单创建#REQ-001 创建订单|REQ-001]]"
rel_exposes:
  - "[[02-架构与契约/接口/API-ORDER-001|API-ORDER-001]]"
rel_reads:
  - "[[02-架构与契约/数据库/表/TABLE-ORDER-001|TABLE-ORDER-001]]"
```

受控关系目录至少包括：

- 要求（`requires`）
- 实现（`implements`）
- 对外提供（`exposes`）
- 消费或使用（`consumes`）
- 产生（`produces`）
- 读取（`reads`）
- 写入（`writes`）
- 依赖（`depends_on`）
- 由其验证（`verified_by`）
- 由证据证明（`evidenced_by`）
- 执行变更工作（`executes`）
- 变更目标（`changes`）
- 由来源支撑（`supported_by`）
- 替代旧版本（`supersedes`）

每条关系同时包含语义类型、目标知识项 ID 和目标文件内部链接。关系只保存一个规范方向，反向关系由检查器动态计算，避免双向链接由人工重复维护后产生不一致。Obsidian 图谱负责展示文件级关联；知识项级关系和锚点由 Context Atlas 检查器解析。

### 6.2 影响分级

知识项发生变化后，检查器结合字段变化和关系图输出：

- 必须处理（机器结果 `required`）：规则能够确定必须同步更新；
- 需要人工复核（机器结果 `review_required`）：存在依赖关系，必须人工判断；
- 提示信息（机器结果 `informational`）：可能相关，仅用于提示。

影响分析产生候选清单和 Proposal，不自动批准或改写关联文档。

## 7. 复杂业务需求表达

复杂需求不应被压缩到一个功能文档中。采用“需求”（`requirement`）和“变更集”（`change_set`）组织多对多关系：

```text
REQ-REFUND-001
├── FEATURE-ORDER-REFUND
├── FEATURE-PAYMENT-REFUND
├── API-REFUND-CREATE
├── API-PAYMENT-CALLBACK
├── TABLE-REFUND
└── AC-REFUND-001..006
```

- 需求表达为什么做、要实现什么和业务约束。
- 功能表达稳定的产品能力。
- 接口、事件和数据表表达技术契约。
- 变更集表达这些知识为何在同一次变化中被创建或修改。
- 验收项表达如何证明需求和功能达到预期。

## 8. 版本与项目发布

面向使用者只保留一个版本：目标项目版本。当前知识库声明它适用的项目版本，每个知识项只记录首次出现、最近修改和弃用时对应的项目版本，不维护独立知识项版本号。

目标项目发版时只封存当前版本变更记录：

```text
90-历史归档/
└── 版本变更/
    └── v3.4.0.md
```

知识库不复制完整快照，不管理或阻止项目发版。完整历史由同仓 Git 记录保存。Context Atlas 只使用默认隐藏的整数 `format_version` 判断知识库格式兼容性，该字段不进入日常业务发版流程。

## 9. 功能、接口、事件与数据库变化控制

功能、接口、事件、数据表和业务规则不维护 Context Atlas 自定义的独立版本号，统一使用稳定知识项 ID，并记录首次出现、最近修改和弃用对应的项目版本。

每次实际变化在变更集中分类为“仅文档变化”“向后兼容变化”“破坏性变化”“已弃用”或“已移除”。关系反向索引负责发现候选影响，当前项目版本的验收证据负责证明已覆盖场景的实际结果。

如果业务项目真实存在公开 API 版本、事件载荷版本、数据库迁移编号或外部供应方版本，知识库应如实记录这些项目事实，但不得因此为所有内部知识项再创建一套版本体系。

## 10. 数据库、多数据源与表级文档

数据库知识按 Oracle、Kingbase、PostgreSQL、MySQL 等产品的真实结构映射“数据源 → 数据库单元 → 可选数据命名空间 → 数据表”。目录可以按项目实际产品裁剪，例如：

```text
02-架构与契约/数据库/
├── 数据源/
│   ├── DS-ORDER.md
│   └── DS-ANALYTICS.md
├── 模式/
│   ├── SCHEMA-ORDER-PUBLIC.md
│   └── SCHEMA-ORDER-AUDIT.md
└── 表/
    ├── TABLE-ORDER.md
    ├── TABLE-ORDER-ITEM.md
    └── TABLE-REFUND.md
```

每张重要表使用一个文档，至少记录：

- 所属数据源和 schema；
- 表用途、边界和负责人；
- 字段中文含义、类型、可空性、默认值和允许存值范围；
- 主键、已有物理外键、唯一约束和索引；
- 枚举值、数值范围、格式、单位和特殊值含义；
- 子表字段到主表字段的逻辑外键映射，并链接主表文件和目标字段；
- 数据分类和敏感级别；
- 数据来源、转换和下游用途；
- 保存和清理规则；
- 对应 migration；
- 该表主动依赖的基础数据对象。

需求、功能、接口和任务从使用方文件引用数据表；数据表不反向维护消费者列表，反向关系和影响范围由检查器生成。原则上不新增数据库物理外键；已经存在的物理外键必须如实记录。

## 11. 原始数据与外部接口数据

知识库不保存生产原始数据，只保存数据契约、位置引用、校验信息和经过脱敏的示例。

多数据源按“数据源 → schema/namespace → 表或数据集 → 字段 → 上下游血缘”表达。

外部接口数据至少记录：

- 来源系统和接口；
- 获取方式和认证方式名称，不保存凭据值；
- 请求/响应 Schema；
- 脱敏示例；
- 获取时间、数据时效性、缓存和刷新规则；
- 数据归属和敏感级别；
- 转换规则；
- 原始数据存储位置引用；
- 本地消费功能。

HTTP API 优先引用 OpenAPI，JSON 数据优先引用 JSON Schema，事件数据使用独立 payload Schema。大体积或敏感数据仅记录安全位置、对象标识、校验和及访问规则。

## 12. 外部依赖能力模型

本议题已经暂缓，不属于当前设计和实现范围。以下内容仅作为以后恢复讨论时的背景，不构成当前要求：

- 依赖标识、来源、供应方和版本；
- 许可证和维护状态；
- 依赖提供的功能清单；
- 本项目实际使用的功能子集；
- 使用该依赖的模块、功能和接口；
- 配置入口；
- 替代方案；
- 升级、兼容和安全风险；
- 官方文档及安全公告引用。

若未来恢复该议题，需要明确区分“依赖拥有的全部能力”和“当前项目实际使用的能力”。

## 13. Skill 与分发方向

- 产品运行入口只面向支持 Skill 的 Agent。
- 内容模型保持尽可能工具无关。
- `context-atlas` Skill 是插件内真正执行知识库工作的能力，不再单独复制一套规则。
- Context Atlas 仓库直接作为一个仅包含 Skill 的 Plugin（插件）根目录；Codex 与 Claude Code 分别读取自己的薄清单，但共享同一个 `skills/context-atlas/`，不复制规则正文。
- 第一版正式支持 Codex 与 Claude Code；后续可以逐步增加 Qoder、Trae 等支持 Skill 的 Agent，但新增平台不得改变核心知识规范。
- 第一阶段不引入 MCP 服务或界面；后续只有在本地 Skill 无法满足受控工具调用时才增补。
- 插件更新与目标项目知识库迁移必须分离，更新插件不能自动改写业务项目中的知识库。

## 14. 当前能力差距

| 领域 | 当前状态 | 未来需要 |
| --- | --- | --- |
| 文档格式 | Markdown、YAML、部分 Schema | 每类知识的完整 Schema、模板和使用契约 |
| CRUD | 有初始化和更新协议雏形 | 完整 Create/Read/Update/Delete 契约 |
| 引用 | 有来源和部分引用链 | 类型化关系、反向索引和影响分析 |
| 需求 | 主要使用功能卡表达 | 需求、业务场景、业务规则和变更集 |
| 发布 | 依赖 Git 历史 | 按项目版本封存一份版本变更记录，不建设独立发布系统 |
| 接口变化 | 无专门模型 | 稳定 ID、统一变化等级、关系影响和验收证据 |
| 数据库 | 有目录和示例 | 数据源、数据库结构、表、迁移记录和血缘模型 |
| 外部数据 | 数据资产基础模型 | 获取、格式、时效、转换、存储位置和消费关系 |
| 外部依赖 | 目录级说明 | 当前暂缓，不纳入本轮实现 |
| Agent 支持 | Skill 与非 Skill 降级入口并存 | 仅承诺支持可适配 Skill 的 Agent |
| 分发 | 仓库内 standalone Skill | 安装、更新、版本固定、卸载和验证 |

## 15. 冲突与必须替代的现行设计

### CONFLICT-001：非 Skill Agent 支持范围

- 现行设计：通用协议文档为不支持 Skill 的 Agent 提供等价入口。
- 用户新方向：不再支持不能适配 Skill 的 Agent。
- 已批准方向：只承诺支持能够适配 Skill 的 Agent；实现阶段需要创建 ADR，替代现有范围和架构表述。

### CONFLICT-002：项目自身机器入口缺失

- Skill 检查流程要求读取知识库根 `knowledge-base.yaml`。
- 当前 `doc-atlas/` 不包含该文件。
- 所需动作：先确认本项目知识库是否必须完全遵守自身初始化产物契约，再决定补齐或修订协议。

## 21. 议题一：知识库部署位置与版本归属

### 21.1 状态

已批准（机器状态 `approved`）

### 21.2 方案 A：目标项目同仓，作为规范默认

每个目标项目在自己的 Git 仓库根目录保存唯一知识库 `doc-<项目名>/`。业务代码和知识库共享 commit、tag、分支、代码评审与发布流程。

优点：

- 代码变化和知识变化可以原子提交；
- 项目 tag 能精确定位对应知识快照；
- 影响分析可以直接读取同一工作树中的代码、配置和文档；
- 不需要跨仓库同步协议；
- 最符合“知识库版本跟随项目版本”的目标。

限制：

- 多仓业务域会产生多个项目知识库；
- 跨仓库需求需要额外的聚合知识，而不能塞进任一项目知识库；
- 某些组织可能不希望全部知识对代码仓库成员可见。

### 21.3 方案 B：知识库独立仓库

知识库保存在独立 Git 仓库，通过项目仓库地址、commit、tag 和发布版本建立映射。

优点：

- 可以独立控制知识访问权限；
- 适合跨多个代码仓库的统一业务知识；
- 文档发布节奏可以与代码不同。

限制：

- 代码和知识无法原子提交；
- 必须实现双仓同步、版本绑定和失败恢复协议；
- 容易出现项目已经发布而知识库尚未同步的漂移；
- 影响分析和审计复杂度显著增加。

### 21.4 方案 C：同仓项目知识库加独立聚合层

每个项目仍按方案 A 保存权威知识库；另建只保存跨项目需求、业务能力地图和项目版本引用的聚合知识库。聚合层不复制项目内部接口、表和实现文档。

优点：

- 保留项目内原子版本关系；
- 能表达跨多个仓库的复杂业务需求；
- 聚合层只引用各项目发布基线，避免复制全部文档。

限制：

- 需要定义项目知识库与聚合知识库的权威边界；
- 需要额外的跨仓引用和发布兼容检查；
- 不适合作为第一阶段同时实现的最小范围。

### 21.5 已批准方案

采用方案 A 作为 Context Atlas 的规范默认和第一阶段唯一部署模型：目标知识库必须与目标项目代码同仓，并随同一 commit、tag 和发布过程演进。

方案 C 作为未来可选扩展，用于确有多个独立代码仓库的业务域。聚合层只能引用项目知识库的已发布基线，不取代项目内知识库。第一阶段不支持方案 B 的“项目知识库完全独立存储”。

### 21.6 已确认决策

已批准方案 A：

- 目标知识库必须位于业务代码的同一个 Git 仓库；
- 知识和代码共享 commit、tag、分支、评审与发布流程；
- 方案 B 的独立知识库仓库不进入当前产品范围；
- 方案 C 的跨项目聚合层保留为未来扩展，不属于第一阶段。

## 22. 议题二：权威文档格式

### 22.1 状态

已批准（机器状态 `approved`）

### 22.2 方案 A：Markdown 为权威载体

每个知识项以 Markdown 文件为权威来源，YAML frontmatter 保存机器字段，正文保存需要人和 Agent 阅读的内容。JSON Schema 检查 frontmatter 和必要正文结构。OpenAPI、JSON Schema、SQL migration 等专业契约作为独立文件，由 Markdown 知识项引用。

优点：

- 人和 Agent 可以直接阅读和修改；
- Git diff 清晰；
- 当前仓库迁移成本最低；
- 不需要生成步骤才能阅读知识。

限制：

- 复杂结构化数据不适合全部写入 Markdown；
- 正文语义只能做有限的确定性检查；
- 必须严格规定哪些字段属于 frontmatter，哪些内容属于正文。

### 22.3 方案 B：YAML/JSON 为权威载体，Markdown 自动生成

知识内容全部保存在结构化 YAML 或 JSON 中，Markdown 只是生成后的阅读视图。

优点：

- 字段级校验和自动处理能力最强；
- 容易构建查询、索引和关系图；
- 格式歧义较少。

限制：

- 人工编写和评审体验较差；
- 复杂业务说明容易退化成大量字符串字段；
- 需要生成器并处理生成文件漂移；
- 与当前“可直接阅读的 Markdown 知识库”方向差异较大。

### 22.4 方案 C：中央清单为权威元数据，Markdown 为权威正文

中央 registry 保存所有知识项的 ID、版本、状态和关系；各 Markdown 文件只保存正文及少量定位信息。

优点：

- 全局查询和关系遍历简单；
- 可以集中检查 ID、版本和关系；
- Markdown 正文保持简洁。

限制：

- 一项知识被拆成两个权威来源；
- 修改时容易只更新 registry 或只更新 Markdown；
- 合并冲突集中在单个清单文件；
- 不利于知识项独立复制、评审和归档。

### 22.5 已批准方案

采用方案 A，并明确“按内容类型选择原生权威格式”：

- 业务知识、设计说明和治理信息：Markdown + YAML frontmatter；
- API 契约：OpenAPI、AsyncAPI、Protocol Buffers 或相应原生契约文件；
- JSON 数据结构：JSON Schema；
- 数据库变化：项目实际使用的 migration/DDL 文件；
- 大型图形或二进制文件：只保存受控引用和必要元数据。

Markdown 知识项负责解释用途、业务语义、负责人、版本、来源和关系，并引用专业契约文件。专业契约文件负责机器可执行的结构定义，不在 Markdown 中重复维护一份完整副本。

根 `knowledge-base.yaml` 只作为知识库机器入口，记录规范版本、项目标识、目录、发布状态和索引位置；它不复制所有知识项内容，也不成为第二套知识正文。

### 22.6 已确认决策

已批准方案 A：

- Markdown + YAML frontmatter 是业务知识、设计说明和治理信息的权威载体；
- API、事件、数据结构和数据库变化使用适用的原生契约格式；
- Markdown 知识项引用专业契约，不重复维护完整契约副本；
- `knowledge-base.yaml` 只作为机器入口，不成为第二套知识正文。

## 23. 议题三：固定单例文档与可重复实体文档

### 23.1 状态

已批准（机器状态 `approved`）

### 23.2 方案 A：最小单例集，其余全部实体化

只保留少数导航和治理入口为固定单例：

- `README.md`：人和 Agent 的阅读入口；
- `knowledge-base.yaml`：机器入口；
- `CURRENT.md`：当前唯一工作状态；
- `CHANGELOG.md`：当前未发布变更入口；
- 各类型目录的 `README.md`：该类型的读写规则和索引说明。

项目目标、边界、术语、技术栈、需求、功能、模块、接口、数据源、表、依赖、ADR、任务、验收和证据全部作为具有稳定 ID 的实体文档。每类实体可以有一个或多个文件，由类型索引聚合。

优点：

- 所有重要知识都能独立版本化、引用和分析影响；
- 大型项目不会被迫把大量内容堆进单个固定文档；
- 新增知识类型不需要不断增加根级固定文件；
- 适合复杂需求、多模块、多数据源和多接口项目。

限制：

- 小型项目文件数量较多；
- 需要可靠的索引和读取规则；
- 初始化模板必须允许空目录或空索引。

### 23.3 方案 B：当前核心总览继续保持固定单例

项目目标、边界、能力地图、术语、技术栈、架构、开发规则和测试规则继续使用固定文件；只有需求、功能、接口、表、依赖、任务、ADR 和验收等使用实体文档。

优点：

- 延续当前目录和阅读习惯；
- 小型项目入口集中；
- 初次使用时容易找到核心内容。

限制：

- 技术栈、能力和架构规模增长后单文件会变大；
- 单个段落或条目难以稳定引用和独立版本化；
- 文档级影响分析粒度较粗；
- 固定文件与实体文件的边界容易随项目规模变化。

### 23.4 方案 C：所有知识实体化，单例文件全部生成

所有知识都保存为实体记录，README、CURRENT、能力地图和其他总览全部由检查器或生成器产生。

优点：

- 数据模型最统一；
- 索引和视图可以按需生成；
- 不存在人工维护汇总文档的问题。

限制：

- 必须依赖生成器才能获得良好阅读体验；
- 生成文件与源实体需要严格隔离；
- 与“仓库克隆后可直接阅读”的目标存在张力；
- 当前阶段的实现和迁移成本最高。

### 23.5 已批准方案

采用方案 A，但规定“稳定 ID 的实体文档可以在小项目中聚合存放”：

- 权威单位是知识项 ID，不强制所有知识项一项一个文件；
- 需求、接口、表、外部依赖等高变更或高引用对象默认一项一个文件；
- 术语、技术栈条目等短小知识允许多个实体聚合在一个 Markdown 文件中，但每个条目仍须具有稳定 ID；
- 当聚合文件超过规定复杂度或引用需求增加时，可无损拆分，知识项 ID 不变；
- README 和索引只承担导航与读写规则，不复制实体正文。

这种模型把“知识项”与“物理文件”分离：影响分析、版本和引用针对知识项 ID，而不是依赖文件路径。

### 23.6 已确认决策

已批准方案 A：

- 只保留最小固定入口，其余知识采用实体模型；
- 权威引用和版本以知识项 ID 为单位；
- 不强制知识项与物理文件一一对应；
- 高变更、高引用对象默认一项一个文件；
- 聚合知识项拆分文件时保持知识项 ID 不变。

## 24. 议题四：语义关系与 Obsidian 文件链接

### 24.1 状态

已批准（机器状态 `approved`）

### 24.2 已确认约束

- 关系必须表达语义类型，例如 implements、reads、writes。
- 关系必须定位目标知识项 ID。
- 关系必须包含 Obsidian 能识别的内部链接，使知识图谱形成源文件到目标文件的边。
- 文件移动或重命名不能改变知识项 ID。
- 检查器必须验证链接目标文件存在，并且目标知识项 ID 确实存在于该文件。
- Obsidian 官方 Properties 不支持嵌套属性，因此不采用嵌套 `relations:` 对象作为规范格式。
- Obsidian 图谱以文件为节点、以内链为边；锚点可以精确定位知识项，但不会把同一文件内的知识项拆成多个图谱节点。

### 24.3 方案 A：扁平类型化链接属性

每种关系使用一个 `rel_<关系类型>` 列表，列表元素是带知识项 ID 显示名的 Obsidian 内部链接：

```yaml
---
id: FEATURE-ORDER-001
rel_implements:
  - "[[01-需求/订单需求|REQ-001]]"
rel_exposes:
  - "[[02-架构与契约/接口/API-ORDER-001|API-ORDER-001]]"
rel_reads:
  - "[[02-架构与契约/数据库/表/TABLE-ORDER-001|TABLE-ORDER-001]]"
rel_writes:
  - "[[02-架构与契约/数据库/表/TABLE-ORDER-002|TABLE-ORDER-002]]"
rel_depends_on:
  - "[[02-架构与契约/外部依赖/DEP-PAYMENT-001|DEP-PAYMENT-001]]"
rel_verified_by:
  - "[[03-实施与验收/验收项/AC-ORDER-001|AC-ORDER-001]]"
---
```

如果目标知识项位于聚合文件中，则链接必须带精确锚点，例如：

```yaml
rel_implements:
  - "[[01-需求/A#^REQ-001|REQ-001]]"
```

优点：

- Obsidian 原生识别文件链接并绘制知识图谱；
- 关系类型、目标路径和目标 ID 都在同一个值中；
- 没有第二套重复关系字段；
- YAML 列表适合 Schema 和检查器解析。

限制：

- 文件移动时需要依赖 Obsidian 自动更新链接或由检查器、迁移工具修复路径；
- 聚合文件需要稳定锚点；
- 属性名称数量随关系类型增加。

### 24.4 方案 B：ID 关系为权威，另加 Obsidian 链接列表

保留原来的 ID 关系，再单独维护文件链接：

```yaml
relations_implements: [REQ-001]
links_implements:
  - "[[01-需求/A#^REQ-001|REQ-001]]"
```

优点：

- 机器 ID 字段简单；
- 文件路径和逻辑 ID 分离。

限制：

- 同一关系维护两份数据；
- ID 与链接容易漂移；
- 每次修改都需要强制同步两个字段。

### 24.5 方案 C：正文关系章节作为权威

frontmatter 只保存基本字段，在正文中使用固定表格或列表：

```markdown
## 关系

- implements: [[01-需求/A#^REQ-001|REQ-001]]
```

优点：

- 人工阅读最直观；
- Obsidian 可以识别内部链接；
- 不受 Properties 嵌套限制。

限制：

- 检查器需要解析 Markdown 结构；
- 人工修改表格或标题可能破坏机器读取；
- 不如 YAML 属性适合查询和批量处理。

### 24.6 已批准方案

采用方案 A。每条关系使用 `rel_<type>` 扁平属性，并把“目标文件路径 + 可选锚点 + 目标知识项 ID”编码在一个 Obsidian 内部链接中。

检查器建立全局 `ID → 文件路径 + 锚点` 索引，然后验证：

1. 链接目标文件存在；
2. 显示 ID 与目标知识项 ID 一致；
3. 聚合文件中的锚点存在并唯一；
4. 关系类型允许连接该源类型和目标类型；
5. 同一关系没有重复或互相矛盾的目标。

为了兼容普通 Markdown 工具，后续还需单独确认内部链接采用 Wikilink，还是由工具生成标准 Markdown 链接；Obsidian 官方同时支持两者，但 YAML Properties 中 Wikilink 更简洁。

### 24.7 已确认决策

已批准方案 A：

- 以 `rel_<type>` 扁平 YAML 属性保存类型化关系；
- 每条关系同时包含目标文件内部链接、可选锚点和目标知识项 ID；
- 该表示是关系的唯一权威来源，不再维护独立 ID 列表；
- Obsidian 展示文件级图谱，Context Atlas 检查器负责知识项级解析和影响分析。

### 24.8 外部依据

- [Obsidian Internal links](https://obsidian.md/help/links)：说明 Wikilink、Markdown link、目录路径、标题和块锚点格式，以及文件重命名时自动更新内部链接的能力。
- [Obsidian Properties](https://obsidian.md/help/properties)：说明 YAML Properties 的列表可以包含带引号的内部链接，同时明确嵌套 Properties 当前不受支持。
- [Obsidian Graph view](https://obsidian.md/help/plugins/graph)：说明图谱节点代表笔记文件，图谱边来自文件之间的内部链接。

## 25. 议题五：知识 CRUD 与生命周期

### 25.1 状态

已批准（机器状态 `approved`）

### 25.2 共同前提

“增删改查”（机器和技术文档中可标识为 `CRUD`）的操作对象是知识项 ID，不是物理文件。一次文件修改可以包含多个知识项操作；一次知识项变更也可以同时修改 Markdown、专业契约和关系引用。

操作结果必须记录：

- 操作类型；
- 目标知识项 ID；
- 变更前后版本；
- 变更来源；
- 操作者和确认者；
- 直接与候选影响；
- 所属变更集（机器标识 `change_set`，表示把同一次业务或技术变化涉及的多个知识项组织在一起）；
- 验证结果。

### 25.3 方案 A：按知识状态分级管理

不同状态采用不同写入门槛：

#### Create

- Agent 可以直接创建“草稿”（机器状态 `draft`）或“待确认”（机器状态 `proposed`）知识，但必须记录来源。
- 进入“已批准”（机器状态 `approved`）前必须展示变更提案（机器标识 `proposal`，表示供用户审阅的候选修改）并获得项目责任人明确确认。
- 新知识项获得永久 ID；批准后不得复用或改变该 ID。

#### Read

- 读取不改变知识状态。
- 默认读取当前有效版本，并同时提供来源、关系、版本和影响状态。
- 历史版本只能作为背景，不能覆盖当前有效知识。

#### Update

- “草稿”和“待确认”知识可以在保留来源的前提下直接修订。
- “已批准”知识的实质性内容、关系、契约或兼容性变化必须先形成变更提案。
- 拼写、排版、失效链接修复等非语义变更可以直接修改，但必须通过检查器证明没有改变知识语义、ID、版本和关系。
- 已批准知识更新后产生新版本；旧版本进入“已被替代”（机器状态 `superseded`），不能被静默覆盖。

#### Delete

- 从未批准且没有被其他知识引用的“草稿”或“待确认”知识可以物理删除。
- 已批准、曾发布或被引用的知识项不得物理删除，只能进入“已弃用”（`deprecated`）、“已被替代”（`superseded`）或“已归档”（`archived`）状态。
- 删除前必须执行反向引用和影响检查；存在引用时必须先更新或明确保留这些引用。

优点：

- 审批成本与知识风险匹配；
- 日常草稿整理不会过度繁琐；
- 已批准知识和发布历史受到严格保护。

限制：

- 必须定义“语义变更”和“非语义变更”的检查边界；
- Agent 需要正确识别目标知识当前状态。

### 25.4 方案 B：所有写操作都必须先批准

任何新增、修改、删除，包括草稿和格式修复，都必须先展示 Proposal 并获得确认。

优点：

- 治理规则最简单；
- 用户始终掌握所有文件变化。

限制：

- 操作成本很高；
- 草稿整理和机械修复也会频繁打断用户；
- 大型知识库难以维护。

### 25.5 方案 C：Git 评审即批准

Agent 可以直接修改所有知识，Pull Request 或 commit review 作为统一批准机制。

优点：

- 与常规代码协作流程一致；
- 变更集中在 Git diff 中评审。

限制：

- Git 合并不能可靠表达具体知识项由谁批准；
- 自动化合并可能绕过业务确认；
- 难以区分仓库写入、内容确认和发布批准三种行为。

### 25.6 已批准方案

采用方案 A，并增加以下确定性规则：

- “已批准”“已弃用”“已被替代”“已归档”等受治理状态的变化必须引用变更集；
- 检查器根据文档头部元数据（技术名称 `frontmatter`）、正文规范区和专业契约的差异判断“可能的语义变更”，无法确定时一律归入“需要人工复核”（机器结果 `review_required`）；
- Git commit/PR 是变更载体和审计证据，但不自动等价于业务内容批准；
- 物理删除只允许用于从未批准、未发布、无引用的候选知识；
- 所有批量操作必须先输出目标 ID 和影响清单，禁止用目录级覆盖代替知识项操作。

### 25.7 已确认决策

已批准方案 A：

- 草稿和待确认知识允许在保留来源的前提下受控维护；
- 已批准知识的业务含义变化必须经过变更提案、变更集、影响分析和明确确认；
- 业务含义变化更新 `last_changed_in` 并由变更集记录；如果由新的知识项替代旧知识项，旧知识项标记为已被替代并链接替代目标；
- 只有从未批准、从未发布、没有引用的候选知识可以物理删除；
- 代码仓库评审是变更和审计证据，但不自动等于业务内容批准。

## 26. 中文优先与术语规范

### 26.1 状态

已批准（机器状态 `approved`）

### 26.2 面向用户的表达规则

- 用户文档、Agent 提问、检查报告、错误信息和设计评审必须以中文为主要语言。
- 不假设使用者理解英文缩写或专业术语。
- 英文机器标识首次出现时，必须采用“中文名称（机器标识 `english_name`，含义说明）”格式。
- 后续段落优先使用中文名称；只有展示配置、Schema、命令或源文件字段时才直接使用英文标识。
- 每一种知识模板必须包含“如何阅读”和“何时使用”的中文说明。
- 错误报告不能只输出字段名和错误码，必须说明问题、影响和用户可以采取的动作。

### 26.3 机器标识规则

Schema 字段、状态值、关系类型、文件 ID 和命令可以保留稳定英文，以支持跨平台解析和版本兼容，但必须在术语表中维护唯一中文名称。

示例：

| 中文名称 | 机器标识 | 含义 |
| --- | --- | --- |
| 增删改查 | `CRUD` | 创建、读取、修改和删除四类知识操作 |
| 草稿 | `draft` | 尚在整理、未提交确认的知识 |
| 待确认 | `proposed` | 已形成候选内容，等待责任人确认 |
| 已批准 | `approved` | 已由责任人明确确认的当前有效知识 |
| 变更提案 | `proposal` | 修改正式知识前提交给责任人审阅的候选变化 |
| 变更集 | `change_set` | 将同一次变化涉及的多个知识项组织在一起的记录 |
| 已被替代 | `superseded` | 已有新版本取代、仅保留历史用途的知识 |
| 已弃用 | `deprecated` | 仍可识别但不建议继续使用的知识 |
| 已归档 | `archived` | 只作为历史背景保存、不是当前基线的知识 |
| 需要人工复核 | `review_required` | 检查器发现可能影响，但不能自动判断内容是否必须修改 |
| 文档头部元数据 | `frontmatter` | Markdown 文件顶部由 `---` 包围的结构化 YAML 数据 |

### 26.4 术语表质检

检查器应验证：

- 受控英文机器标识在术语表中存在中文名称；
- 用户可见模板首次出现专业术语时提供解释或链接到术语表；
- 同一个机器标识没有多个相互冲突的中文名称；
- 检查报告能够从机器字段映射到中文说明。

## 27. 议题六：复杂业务需求的多对多表达

### 27.1 状态

已批准（机器状态 `approved`）

### 27.2 需要解决的问题

一个复杂业务需求可能同时涉及：

- 多个稳定功能；
- 多个接口或事件；
- 多条业务规则；
- 多张数据库表；
- 多个外部依赖；
- 多个验收项；
- 多个版本或发布阶段。

这些关系不是简单的目录父子关系，而是多对多关系。例如，一个功能可以实现多个需求，一个需求也可以由多个功能共同实现。

### 27.3 方案 A：需求为业务根，变更集组织一次交付

把“需求”和“变更集”分成两类知识：

- **需求**：表达为什么做、要达到什么业务结果、范围和约束。需求具有稳定 ID，可以跨多个项目版本持续存在。
- **变更集**：表达某一次实际修改涉及哪些需求、功能、接口、表、依赖、任务和验收项。变更集在完成并随项目发布后封存。

业务场景和业务规则也作为独立知识项，通过已批准的 `rel_<type>` 内部链接连接：

```yaml
id: REQ-REFUND-001
rel_realized_by:
  - "[[01-功能/FEATURE-ORDER-REFUND|FEATURE-ORDER-REFUND]]"
  - "[[01-功能/FEATURE-PAYMENT-REFUND|FEATURE-PAYMENT-REFUND]]"
rel_constrained_by:
  - "[[01-业务规则/RULE-REFUND-LIMIT|RULE-REFUND-LIMIT]]"
rel_verified_by:
  - "[[03-实施与验收/验收项/AC-REFUND-001|AC-REFUND-001]]"
```

对应的一次交付变更集：

```yaml
id: CHANGE-2026-REFUND-001
rel_addresses:
  - "[[01-需求/REQ-REFUND-001|REQ-REFUND-001]]"
rel_changes:
  - "[[01-功能/FEATURE-ORDER-REFUND|FEATURE-ORDER-REFUND]]"
  - "[[02-架构与契约/接口/API-REFUND-CREATE|API-REFUND-CREATE]]"
  - "[[02-架构与契约/数据库/表/TABLE-REFUND|TABLE-REFUND]]"
```

优点：

- 稳定业务需求与一次实施变化相互分离；
- 能表达跨功能、接口、表和依赖的复杂需求；
- 同一个需求可以分多个版本逐步交付；
- 变更集天然适合作为影响分析、任务和发布封存的边界；
- Obsidian 能展示相关文件之间的关系图。

限制：

- 知识类型和文件数量增加；
- 必须明确需求、功能、业务规则和变更集各自负责表达什么；
- 需要防止把所有文件无差别关联到一个巨大变更集中。

### 27.4 方案 B：以功能为中心吸收需求

不建立独立需求和变更集。每个功能文档直接记录业务背景、相关接口、数据表、依赖、任务和验收项。

优点：

- 文档数量少；
- 简单项目容易理解；
- 与当前功能卡结构接近，迁移成本较低。

限制：

- 一个需求跨多个功能时，业务背景会重复；
- 很难回答“一项需求最终涉及了哪些功能和契约”；
- 功能文档容易变得过大；
- 无法清晰区分稳定功能和某一次版本修改。

### 27.5 方案 C：所有变化都以变更集为中心

每次业务需求都创建一个变更集，功能、接口、表和验收项只作为变更集的组成部分；不单独维护稳定需求知识。

优点：

- 一次交付的范围非常集中；
- 容易对应任务、代码提交和项目版本；
- 适合以版本交付为中心的团队。

限制：

- 长期业务需求会被拆散在多个变更集中；
- 难以查看需求当前完整状态；
- 同一个业务目标跨多个版本时需要人工汇总；
- 变更记录会取代业务知识，长期可读性较差。

### 27.6 已批准方案

采用方案 A，并规定：

- 需求负责“为什么做、要达到什么结果”；
- 业务规则负责“必须始终满足什么约束”；
- 功能负责“系统稳定提供什么能力”；
- 接口、事件和数据表负责“技术上如何交互和存储”；
- 变更集负责“这一次具体修改什么”；
- 任务负责“由谁执行哪些工作”；
- 验收项负责“如何证明结果正确”；
- 发布记录负责“哪些变更集进入了哪个项目版本”。

每种关系必须通过带文件引用的类型化关系表达，不能只在正文中用自然语言提及。

### 27.7 已确认决策

已批准方案 A：

- 需求作为稳定业务根，可以跨多个项目版本持续存在；
- 变更集组织一次实际交付涉及的需求、功能、接口、数据、依赖、任务和验收项；
- 功能、接口、业务规则、数据和验收项保持独立知识身份；
- 所有多对多关系通过带文件引用的类型化关系表达。

## 28. 议题七：项目版本与变更记录封存

### 28.1 状态

已批准（机器状态 `approved`）

### 28.2 已确认的简化边界

- Context Atlas 不建设独立发布管理系统；
- 不负责阻止或批准目标项目发版；
- 不生成复杂发布清单和验收证据清单；
- 不复制完整知识库快照；
- 只解决“知识库当前对应哪个项目版本”和“当前版本变更记录如何封存”。

### 28.3 方案 A：一个项目版本加一份变更记录

知识库只向用户展示一个版本：目标项目版本。

根机器入口记录：

```yaml
project_version: 3.4.0
```

每个知识项不再维护独立版本号，只记录它在哪个项目版本中发生变化：

```yaml
introduced_in: 3.1.0
last_changed_in: 3.4.0
deprecated_in: null
```

项目发版时只做两件事：

1. 将当前 `CHANGELOG.md`（中文名称“当前版本变更记录”）移动到：

   ```text
   90-历史归档/版本变更/v3.4.0.md
   ```

2. 创建新的空白 `CHANGELOG.md`，开始记录下一版本变化。

历史完整内容继续由同仓代码记录保存。Context Atlas 不要求额外发布清单、版本标签或证据索引，也不参与项目发布判断。

优点：

- 使用者只需要理解项目版本；
- 发版动作只有“封存当前变更记录”；
- 可以知道每项知识首次出现和最近修改的项目版本；
- 不复制文档，不污染 Obsidian 图谱；
- 实现和维护成本低。

限制：

- 不能为单个接口或功能表达独立于项目的版本号；
- 查看历史完整内容仍依赖项目代码记录；
- 如果项目本身没有明确版本，必须允许使用日期或内部发布编号。

### 28.4 方案 B：只记录项目版本，不记录知识项变化版本

根机器入口保存当前项目版本。发版时封存 `CHANGELOG.md`，但需求、功能、接口、表等知识项不记录首次出现和最近修改的项目版本。

优点：

- 字段最少；
- 发版流程与方案 A 一样简单；
- 对小型项目足够。

限制：

- 无法直接知道某个接口或功能从哪个版本开始存在；
- 需要搜索历史变更记录才能定位知识项变化；
- 后续做兼容性和影响判断时信息不足。

### 28.5 方案 C：不提供版本封存能力

Context Atlas 不记录项目版本，也不封存变更记录，完全依赖项目自己的代码仓库和发布工具。

优点：

- 产品最简单；
- 没有额外发版操作。

限制：

- 不满足“知识库版本跟随项目版本”的原始目标；
- 知识库无法说明当前内容适用于哪个项目版本；
- 使用者必须到其他工具中查找版本变化。

### 28.6 已批准方案

采用简化后的方案 A：

- 用户只看到项目版本，不需要理解多套版本体系；
- 每个知识项只记录首次出现、最近修改和弃用时对应的项目版本；
- 项目发版时只封存一份当前版本变更记录；
- Context Atlas 不管理发版、不阻止发版，也不复制完整知识库。

知识库规范自身的兼容版本可以作为内部机器字段存在，但不进入日常用户流程，只有升级 Skill、模板或检查器时才显示。

### 28.7 已确认决策

已批准简化方案 A：

- 知识库面向使用者只展示一个目标项目版本；
- 知识项只记录首次出现、最近修改和弃用对应的项目版本；
- 项目发版时只封存当前版本变更记录，并创建下一版本的空白变更记录；
- Context Atlas 不管理或阻止项目发版，不生成复杂发布清单，不复制完整知识库。

## 29. 议题八：多数据源、多模式与数据表文档

### 29.1 状态

已批准（机器状态 `approved`）

### 29.2 需要解决的问题

- 一个项目连接多个数据库或其他数据源时如何区分？
- 一个数据库存在多个模式、命名空间或逻辑库时如何表达？
- 每张表是否单独建立文档？
- 字段、主键、外键、索引和迁移文件存在哪里？
- 功能和接口如何关联它们读取或写入的数据表？
- 数据库结构变化后如何判断受影响的功能和接口？

“模式”在不同数据库中可能叫 schema、database、namespace 或 keyspace，面向用户统一称为“数据命名空间”，文档中同时保留实际数据库使用的名称。

已确认外键规则：

- 项目原则上不使用或新增数据库物理外键；
- 当前数据库已经存在物理外键时，知识库必须按实际结构保存；
- 无论是否存在物理外键，只要业务上存在主子表引用，都必须记录逻辑外键；
- 外键关系统一由子表文档指向主表文件，并记录子字段和主字段；
- Context Atlas 只负责记录与检查，不自动删除现有物理外键，也不替项目修改数据库。

### 29.3 方案 A：数据源、数据库单元、可选命名空间、数据表分层实体

根据数据库产品的真实结构建立分层知识项：

```text
02-架构与契约/数据库/
├── 数据源/
│   ├── DS-ORDER-订单数据库.md
│   └── DS-ANALYTICS-分析数据库.md
├── 数据库单元/
│   ├── DB-ORDER.md
│   └── DB-ORACLE-ORDER-PDB.md
├── 数据命名空间/
│   ├── NS-ORDER-PUBLIC.md
│   └── NS-ORDER-AUDIT.md
└── 数据表/
    ├── TABLE-ORDER-订单表.md
    ├── TABLE-ORDER-ITEM-订单明细表.md
    └── TABLE-REFUND-退款表.md
```

各数据库产品的映射为：

| 数据库产品 | 数据源层 | 数据库单元层 | 数据命名空间层 | 对象层 |
| --- | --- | --- | --- | --- |
| Oracle | 实例或集群连接 | 可插拔数据库；容器数据库作为可选上级拓扑 | Schema/用户拥有的对象集合 | 表、视图等 |
| PostgreSQL | 服务器或集群连接 | Database | Schema | 表、视图、外部表等 |
| KingbaseES | 服务器或集群连接 | 数据库 | 模式 | 表、视图、外部表等 |
| MySQL | 实例或集群连接 | Database/Schema | 不重复建立 | 表、视图等 |

如果数据库产品不存在独立命名空间层，则直接使用“数据库单元 → 数据表”，不创建空壳目录或重复实体。

#### 数据源文档

每个数据库、只读副本、数据仓库或其他持久化数据源一个知识项，记录：

- 用途和负责人；
- 数据库类型和可确认的版本；
- 配置位置和环境变量名称，不保存凭据值；
- 包含的数据命名空间；
- 读写该数据源的模块和外部系统；
- 备份、恢复和安全边界的引用。

#### 数据命名空间文档

每个 schema、逻辑 database、namespace 或 keyspace 一个知识项，记录：

- 所属数据源；
- 数据库中的真实名称；
- 业务用途；
- 包含的数据表；
- 权限和迁移规则。

该层是可选层。只有目标数据库实际存在独立 Schema、模式或类似命名空间时才创建。

#### 数据表文档

项目能够读写或依赖的每张业务表一个独立知识项，默认一表一文件，记录：

- 所属数据源和命名空间；
- 表名、用途、负责人和数据敏感等级；
- 字段名、类型、可空性、默认值和中文含义；
- 字段允许存值，包括枚举值及每个值的中文含义、数值最小值和最大值、字符串格式、长度、正则约束、日期范围以及“其他值”处理规则；
- 主键、外键、唯一约束和索引；
- 数据来源、转换规则和下游用途；
- 保存、清理和归档规则；
- 对应的建表文件或数据库迁移文件引用；
- 物理外键及逻辑外键的子字段、主表文件链接和主字段映射。

数据库定义文件和迁移文件仍是结构变化的专业契约，表文档负责解释业务语义并引用这些文件，不重复创造另一份无法同步的结构定义。

优点：

- 清楚支持多个数据源和多个数据命名空间；
- 每张表都能独立关联功能、接口、需求和迁移文件；
- Obsidian 可以展示数据源、命名空间、表和业务文件的图谱；
- 表变化后的影响范围可以通过读取、写入和依赖关系计算；
- 单表文档规模可控。

限制：

- 表数量多时文件数量较多；
- 需要工具辅助生成表文档骨架和检查字段同步；
- 必须区分业务表、系统表、临时表和完全不受项目控制的外部表。

### 29.4 方案 B：每个数据命名空间一个聚合文档

每个数据源和数据命名空间建立文档，但一个命名空间中的所有表都写在同一个 Markdown 文件中。

优点：

- 文件数量少；
- 可以在一个页面浏览整个命名空间；
- 小型数据库维护简单。

限制：

- 表多时文件会非常大；
- Obsidian 图谱只能显示整个命名空间文件，不能显示每张表的文件节点；
- 单表引用必须依赖标题或块锚点；
- 多人修改不同表时容易产生文件冲突；
- 单表变化的影响分析和版本记录较粗。

### 29.5 方案 C：只引用数据库定义文件，不维护表文档

知识库只记录数据源和数据库定义文件位置。表、字段、索引和约束完全从建表语句、数据库迁移文件或数据库实时结构中读取。

优点：

- 不重复维护数据库结构；
- 文件数量最少；
- 技术结构始终以实际定义为准。

限制：

- 建表语句通常缺少业务用途、中文含义、负责人和数据治理信息；
- 无法通过 Obsidian 图谱查看单表与业务功能的关联；
- 非技术使用者很难阅读；
- 外部表和历史兼容规则难以表达；
- 不能替代业务语义文档。

### 29.6 已批准方案

采用方案 A，并保持以下简化边界：

- 数据源、数据命名空间和业务表是三级实体；
- 项目读取、写入或在业务上依赖的每张表默认一表一文件；
- 数据库系统表、临时表和项目完全不使用的表不进入知识库；
- 字段记录在所属表文档中，不为每个字段单独创建文件；
- 数据库定义和迁移文件负责技术结构，表文档负责业务语义和关系；
- 功能、接口、需求和任务通过 `rel_reads`、`rel_writes`、`rel_depends_on` 等关系引用表文件；表文件不反向维护这些上层文件列表；
- 子表文档负责引用主表文件并记录物理或逻辑字段映射；
- 不因记录逻辑外键而要求数据库创建物理外键；
- 可以由工具生成或更新字段骨架，但业务含义和负责人仍需确认。

### 29.7 已确认决策

已批准修订后的方案 A：

- 按数据库产品真实结构映射“数据源 → 数据库单元 → 可选数据命名空间 → 数据表”；
- 项目读取、写入或依赖的业务表默认一表一文件；
- 每个字段记录中文含义、允许值、范围、格式、空值和默认值；
- 原则上不新增物理外键，已有物理外键如实记录；
- 所有业务主子表引用都记录逻辑外键，由子表链接主表并记录字段映射；
- 功能、接口、需求和任务引用数据表，数据表不反向维护上层业务文件列表。

### 29.8 字段存值范围

每个字段除技术类型和中文含义外，还必须按实际情况记录以下约束：

| 约束 | 示例 |
| --- | --- |
| 枚举值 | `1=待处理`、`2=处理中`、`3=已完成` |
| 数值范围 | 最小值 0，最大值 100 |
| 字符串集合 | `NEW`、`PAID`、`CLOSED` |
| 格式规则 | 手机号、统一社会信用代码、业务编号格式 |
| 长度规则 | 最小长度、最大长度或固定长度 |
| 时间范围 | 不早于创建时间、不晚于失效时间 |
| 空值规则 | 是否允许为空，以及为空的业务含义 |
| 默认值 | 默认值及其业务原因 |
| 开放范围 | 是否允许未列出的其他值，遇到未知值如何处理 |

检查器应区分：

- 数据库已经通过约束强制执行的范围；
- 仅由应用程序或业务规则执行的范围；
- 只有文档说明、尚未确认执行位置的范围。

### 29.9 数据库关系方向

数据库作为基础知识，被需求、功能、接口、任务等上层知识引用：

```text
功能或接口文件
  └── 读取/写入/依赖 → 数据表文件
```

数据表文件不反向列出所有使用它的功能或接口。反向影响由检查器根据全库关系索引计算，Obsidian 通过反向链接展示。

表与表之间的关系按照数据依赖方向记录在子表：

```text
子表文件
  └── 物理外键或逻辑外键 → 主表文件
      └── 子字段 → 主字段
```

统一关系示例：

```yaml
id: TABLE-ORDER-ITEM
rel_logical_parent:
  - "[[02-架构与契约/数据库/数据表/TABLE-ORDER-订单表|TABLE-ORDER]]"
```

正文中的字段映射：

```markdown
| 关系类型 | 子字段 | 主表 | 主字段 | 数据库是否有物理约束 |
| --- | --- | --- | --- | --- |
| 逻辑外键 | `order_id` | [[TABLE-ORDER-订单表|TABLE-ORDER]] | `id` | 否 |
```

如果数据库实际存在物理外键，则同一记录将“数据库是否有物理约束”标记为“是”，并补充真实约束名称。逻辑外键关系始终保留，不依赖数据库是否创建了物理约束。

### 29.10 外部依据

- [Oracle 可插拔数据库](https://docs.oracle.com/en/cloud/paas/base-database/about-pdb/index.html)：Oracle 容器数据库可包含多个可插拔数据库，可插拔数据库包含 Schema 及其对象。
- [PostgreSQL tables](https://www.postgresql.org/docs/current/infoschema-tables.html)：表归属于当前数据库中的 Schema。
- [KingbaseES tables](https://help.kingbase.com.cn/v8.6.7.12/admin/reference/ref-database-parameter/information-schema/tables.html)：表记录包含数据库名、模式名和表名。
- [MySQL SCHEMATA](https://dev.mysql.com/doc/refman/8.0/en/information-schema-schemata-table.html)：MySQL 中 Schema 与 Database 等价。

## 30. 议题九：原始数据与外部接口数据的保存方式

### 30.1 状态

已批准（机器状态 `approved`）

### 30.2 需要解决的问题

- 外部接口返回的原始数据是否直接保存到知识库？
- JSON、XML、CSV、文件、消息等不同格式如何说明？
- 如何保存脱敏示例，避免密码、身份信息和生产数据进入代码仓库？
- 原始数据实际保存在数据库、对象存储或文件目录时，知识库如何定位？
- 外部数据从来源到本地表或业务功能的转换关系如何表达？
- 数据格式发生变化后如何识别受影响文件？

### 30.3 方案 A：知识库存数据契约、位置引用和最小脱敏示例

知识库不保存真实生产原始数据，只保存“数据资产”文档。每一种重要外部或原始数据建立一个知识项，记录：

- 数据来源和负责人；
- 获取方式及接口文件链接；
- 原始格式，例如 JSON、XML、CSV、Excel、二进制文件或消息；
- 字符编码、压缩方式和内容类型；
- 数据结构契约文件；
- 允许字段、字段含义和取值范围；
- 获取频率、时效性、缓存和刷新规则；
- 实际存储位置的安全引用；
- 数据敏感等级和脱敏规则；
- 从原始数据到本地数据表或业务对象的转换规则；
- 消费该数据的功能、接口或任务；
- 一个最小、虚构或不可逆脱敏的示例。

不同格式优先引用原生契约：

| 数据格式 | 推荐结构契约 |
| --- | --- |
| JSON | JSON Schema |
| HTTP 接口 | OpenAPI 中的请求和响应结构 |
| 消息或事件 | AsyncAPI 或独立消息结构文件 |
| XML | XML Schema |
| CSV | 字段清单、分隔符、表头、编码和行规则 |
| Excel | 工作表、列、类型和必填规则 |
| 二进制文件 | 文件格式说明、版本、校验和与解析器引用 |

实际存储位置只记录逻辑位置和配置引用，例如：

```yaml
storage_kind: object_storage
storage_reference: "配置项 DATA_BUCKET 下的 raw/refund/"
credential_reference: "环境变量 DATA_STORAGE_CREDENTIAL"
```

不得保存真实访问地址中的密钥、Token、密码或带签名下载地址。

数据流关系按依赖方向记录：

```text
外部接口或文件来源
  → 原始数据资产
  → 转换规则或处理任务
  → 本地数据表或业务对象
  → 消费功能
```

上层处理任务和功能引用基础数据资产；数据资产不反向维护所有消费者，反向影响由检查器计算。

优点：

- 避免生产数据和敏感信息进入代码仓库；
- 格式、位置、时效和转换关系都可追踪；
- 可以引用本地表、外部接口和处理任务；
- 适合 Obsidian 展示数据来源和流向；
- 不会让知识库因大量数据文件膨胀。

限制：

- 无法直接在知识库查看完整真实样本；
- 需要另有受控存储保存实际数据；
- 示例脱敏是否充分仍需要安全检查。

### 30.4 方案 B：允许保存经过脱敏的完整样本

除数据契约和位置引用外，允许把一份完整脱敏样本保存在知识库，例如：

```text
02-架构与契约/数据资产/样本/退款响应.sample.json
```

优点：

- 开发者和 Agent 可以直接查看完整结构；
- 便于测试解析器和理解边界情况；
- 外部系统不可访问时仍有样本可用。

限制：

- “已经脱敏”很难绝对保证；
- 大样本会增加仓库体积；
- 样本容易过期并与真实接口不一致；
- 可能误把真实数据提交到仓库；
- 需要额外的敏感信息扫描和样本大小限制。

### 30.5 方案 C：知识库只保存外部位置链接

知识库只记录数据存储位置，不保存数据结构、转换规则或示例。

优点：

- 知识库内容最少；
- 不存在样本数据泄露；
- 所有数据都留在原有系统。

限制：

- 无法离线理解数据格式；
- 外部位置失效后知识不可用；
- 无法检查字段、值域和格式变化；
- 很难分析数据变化影响哪些功能和表；
- 不满足知识库自包含的阅读目标。

### 30.6 已批准方案

采用方案 A，并规定：

- 知识库默认不保存真实原始数据；
- 只保存数据契约、存储位置引用、转换关系和最小脱敏示例；
- 示例必须是虚构数据或不可逆脱敏数据，并设置大小限制；
- 完整样本如果确实需要，应作为测试夹具由项目测试规则单独治理，不能冒充知识库文档；
- 所有消费者引用数据资产，数据资产不反向维护消费者列表。

### 30.7 已确认决策

已批准方案 A：

- 知识库不保存真实生产原始数据；
- 保存数据契约、安全位置引用、转换关系和最小虚构或不可逆脱敏示例；
- 完整样本如确有需要，作为测试数据单独治理，不属于知识库正式内容；
- 消费功能和处理任务引用数据资产，数据资产不反向维护消费者列表。

## 31. 议题十：外部依赖及其能力清单

### 31.1 状态

暂缓（机器状态 `deferred`）

### 31.2 需要解决的问题

外部依赖包括但不限于：

- 第三方代码库或软件包；
- 数据库驱动和开发框架；
- 消息中间件、缓存、搜索引擎和对象存储；
- 外部平台提供的软件开发工具包；
- 由其他团队维护的内部公共组件；
- 操作系统组件或项目运行时依赖。

知识库需要区分：

- 依赖本身能够提供哪些能力；
- 当前项目实际使用了哪些能力；
- 哪些功能、接口或任务直接依赖这些能力；
- 版本升级、替换或移除可能影响什么。

### 31.3 方案 A：依赖文档加能力项，项目使用方引用具体能力

每个重要外部依赖建立一个依赖文档。依赖提供的能力作为具有稳定编号的子知识项，保存在依赖文档中；能力较多时可以拆为独立文件。

示例：

```text
02-架构与契约/外部依赖/
├── DEP-REDIS-Redis.md
├── DEP-KAFKA-Kafka.md
└── DEP-PAYMENT-SDK-支付工具包.md
```

依赖文档记录：

- 依赖名称、供应方、来源和当前版本；
- 官方文档和版本说明引用；
- 许可证、维护状态和支持期限；
- 安装或引入位置；
- 配置入口和环境变量名称，不保存配置值；
- 项目允许使用的版本范围；
- 替代方案；
- 升级、兼容、安全和停止维护风险；
- 依赖提供的能力清单。

能力清单示例：

```markdown
| 能力编号 | 能力名称 | 依赖版本 | 项目是否使用 | 官方依据 |
| --- | --- | --- | --- | --- |
| CAP-REDIS-STRING | 字符串读写 | 7.x | 是 | 官方命令文档 |
| CAP-REDIS-PUBSUB | 发布订阅 | 7.x | 否 | 官方命令文档 |
| CAP-REDIS-STREAM | 流式消息 | 7.x | 是 | 官方命令文档 |
```

项目中的功能、接口和任务不只引用依赖文件，还应尽可能引用实际使用的能力编号：

```yaml
rel_depends_on:
  - "[[02-架构与契约/外部依赖/DEP-REDIS-Redis#^CAP-REDIS-STRING|CAP-REDIS-STRING]]"
```

关系方向仍然由使用方指向基础依赖能力。依赖文档不反向维护所有使用方，反向引用和影响范围由检查器计算。

项目没有使用的能力可以记录，但应标记为“未使用”，不能因为依赖具备该能力就推断项目采用了它。能力清单只记录与项目评估、理解、升级或替换相关的能力，不要求复制供应方全部产品手册。

优点：

- 明确区分“依赖具备”和“项目实际使用”；
- 能精确判断依赖能力变化影响哪些功能；
- Obsidian 可以展示功能到依赖文件的关系；
- 升级时可以逐项检查已使用能力的兼容性；
- 不需要把依赖全部文档复制进知识库。

限制：

- 需要维护能力编号和官方来源；
- 大型依赖的能力边界需要人工筛选；
- 依赖升级时可能需要更新能力清单。

### 31.4 方案 B：依赖文档只记录项目实际使用能力

每个依赖建立文档，但只列出当前项目已经使用的功能，不记录依赖提供但项目未使用的能力。

优点：

- 文档简洁；
- 维护成本较低；
- 使用范围一目了然。

限制：

- 无法区分“未评估”和“确认未使用”；
- 替换依赖或扩展能力时需要重新查阅全部外部文档；
- 难以说明为什么选择或没有选择某项能力；
- 对升级和替代评估帮助有限。

### 31.5 方案 C：只记录依赖名称和版本

知识库只记录依赖名称、版本和安装位置，能力信息完全依赖外部官方文档或代码扫描。

优点：

- 内容最少；
- 可以从包管理文件自动生成；
- 几乎没有人工维护成本。

限制：

- 无法知道项目为什么使用该依赖；
- 无法判断项目使用了哪些能力；
- 依赖升级时难以分析业务影响；
- 无法形成能力到功能的明确引用关系；
- 不满足用户提出的外部依赖功能清单要求。

### 31.6 暂缓前建议

推荐方案 A，但限制能力清单范围：

- 必须记录项目已经使用的能力；
- 必须记录与替换、升级、安全或架构决策相关但当前未使用的能力；
- 不要求穷举依赖产品的全部功能；
- 每项能力必须有中文名称、稳定编号、适用依赖版本和官方来源；
- 使用方引用具体能力，依赖不反向维护使用方；
- 包管理文件或锁定文件负责证明实际版本，依赖文档负责解释能力、用途和风险。

### 31.7 暂缓决定

本议题已暂缓：

- 当前阶段不要求建立外部依赖能力清单；
- 本节 A、B、C 方案只作为未来背景，不形成正式产品要求；
- 后续只有用户重新将该议题纳入范围时才恢复评审。

## 32. 议题十一：文档变化与业务影响分析

### 32.1 状态

已批准（机器状态 `approved`）

### 32.2 需要解决的问题

- 一个字段、接口、规则或文档发生变化后，哪些文件必须同步修改？
- 哪些文件只需要人工检查，不一定修改？
- 如何避免检查器误判业务结论？
- 如何区分直接影响和间接影响？
- 一次变化涉及多个知识项时，如何集中记录分析结果？
- 如何防止存在未处理影响时把正式知识错误地标记为已完成？

影响分析的前提是已经批准的类型化关系。检查器通过 `rel_<type>` 内部链接建立关系图和反向引用索引。

### 32.3 方案 A：关系规则加变更类型，输出三级影响结果

每次修改先识别“变化了什么”，再结合关系类型计算候选影响。

#### 第一步：识别变化类型

变化类型包括：

- 纯排版或错别字变化；
- 中文说明变化；
- 业务规则变化；
- 接口字段新增、删除或类型变化；
- 数据表字段、值域或逻辑外键变化；
- 关系新增、删除或目标变化；
- 状态变化，例如弃用或被替代；
- 专业契约文件变化。

#### 第二步：根据关系计算影响

检查器维护“源类型 + 变化类型 + 关系类型 → 影响等级”的规则。例如：

| 变化 | 关联关系 | 结果 |
| --- | --- | --- |
| 需求正文只改错别字 | 功能实现该需求 | 无业务影响 |
| 业务规则的允许值变化 | 功能受该规则约束 | 需要人工复核 |
| 接口删除响应字段 | 功能使用该接口 | 必须处理 |
| 数据表字段类型变化 | 接口或任务读取该表 | 必须处理 |
| 数据表字段中文说明变化 | 功能读取该表 | 需要人工复核 |
| 文档文件移动但知识项 ID 和链接目标不变 | 所有引用 | 无业务影响，只检查链接 |

#### 第三步：输出三级结果

- **必须处理**（机器结果 `required`）：检查规则能够确定关联知识或契约必须修改、重新验证或明确豁免。
- **需要人工复核**（机器结果 `review_required`）：存在关联和潜在影响，但检查器不能判断业务是否真的需要修改。
- **提示信息**（机器结果 `informational`）：用于告知关系或非业务变化，不阻止后续流程。

影响分析结果保存到本次变更集中：

```markdown
| 来源知识 | 变化内容 | 受影响知识 | 影响等级 | 处理结果 | 确认人 |
| --- | --- | --- | --- | --- | --- |
| TABLE-ORDER | status 增加值 4 | API-ORDER | 需要人工复核 | 接口原样透传，无需修改 | 项目责任人 |
```

处理状态包括：

- 待处理；
- 已修改；
- 已确认无需修改；
- 已由责任人批准暂不处理。

Context Atlas 不自动修改关联文档，也不自动判断业务含义。它只生成影响候选、检查处理状态，并要求结论引用相关文件和确认来源。

优点：

- 能区分技术上确定的影响和需要人工判断的影响；
- 能处理字段级、关系级和文件级变化；
- 影响结果保存在变更集中，便于追踪；
- 可以逐步增加规则，不需要一开始覆盖所有业务；
- 不会把检查器误当作业务决策者。

限制：

- 需要维护变化类型和关系规则；
- 首期规则不完整时会产生较多“需要人工复核”；
- 只有关系引用完整时分析结果才可靠。

### 32.4 方案 B：只按关系深度提示所有关联文件

知识变化后，检查器列出一层或多层关联文件，不区分变化内容，也不判断影响等级。

例如：

```text
TABLE-ORDER 变化
├── API-ORDER
├── FEATURE-ORDER
└── AC-ORDER
```

优点：

- 实现简单；
- 不容易错误判断“必须修改”；
- 可以直接利用 Obsidian 文件关系图。

限制：

- 改错别字和删字段会得到同样结果；
- 关联多时产生大量无意义提示；
- 用户无法判断优先处理什么；
- 不满足“判断是否对业务有相关影响”的目标。

### 32.5 方案 C：由 Agent 阅读所有关联文档后直接给出业务结论

检查器只提供关系图，Agent 阅读变更和关联文档，然后直接判断哪些文件需要修改以及业务影响。

优点：

- 能结合自然语言和项目上下文；
- 不需要维护大量确定性规则；
- 对复杂业务变化可能给出更具体的说明。

限制：

- 同一变化可能被不同 Agent 得出不同结论；
- 结论难以重复验证；
- Agent 可能漏读关联文件或过度推断；
- 不适合作为文档质检的唯一依据；
- 与“AI 推测不能自动成为批准事实”的原则冲突。

### 32.6 已批准方案

采用方案 A，并限制自动判断范围：

- 检查器只对明确规则输出“必须处理”；
- 无法确定时统一输出“需要人工复核”；
- Agent 可以解释可能影响并提出建议，但结论仍需责任人确认；
- 所有影响结果必须引用来源文件和受影响文件；
- 影响分析记录属于变更集的一部分；
- 首期优先覆盖接口字段、数据表字段和值域、逻辑外键、业务规则、状态和关系变化；
- 不追求第一版自动理解所有正文语义。

### 32.7 已确认决策

已批准方案 A：

- 根据变化类型和关系规则输出“必须处理、需要人工复核、提示信息”三级结果；
- 只有明确规则可以输出“必须处理”，无法确定时必须人工复核；
- 影响分析结果保存在变更集中，并引用来源文件和受影响文件；
- 检查器不自动修改关联文件，也不裁决业务含义。

## 33. 议题十二：每类文档的保存与使用说明

### 33.1 状态

已批准（机器状态 `approved`）

### 33.2 需要解决的问题

- 使用者如何知道某类文档保存在哪个目录？
- 如何知道应该在什么情况下创建、读取、修改或归档？
- 如何知道哪些内容是必填、哪些内容可以省略？
- 如何知道文档应该引用哪些上游和下游知识？
- 如何知道谁负责填写业务含义、谁负责确认？
- 如何避免每个实体文件重复大段使用说明？

### 33.3 方案 A：每类目录提供中文使用契约，实体模板提供简短指引

每一种知识类型都有一个目录级 `README.md`，作为该类文档的中文使用契约。例如：

```text
01-需求/README.md
01-功能/README.md
02-架构与契约/接口/README.md
02-架构与契约/数据库/数据表/README.md
```

每份使用契约必须说明：

1. 这类文档解决什么问题；
2. 哪些人和 Agent 在什么情况下读取；
3. 什么情况下创建；
4. 什么变化会触发更新；
5. 什么情况下弃用、替代或归档；
6. 文档的保存路径和命名规则；
7. 必填字段及其中文解释；
8. 正文必须包含的章节；
9. 允许和禁止的关系类型；
10. 内容来源和确认责任；
11. 一个最小正确示例；
12. 常见错误和检查规则。

实体模板只保留简短中文提示和到使用契约的 Obsidian 链接，避免复制完整说明：

```markdown
> 使用说明：[[01-需求/README|需求文档如何创建和维护]]
```

知识库根 `README.md` 提供面向普通使用者的总导航：

- 我想了解项目，应先读什么；
- 我想新增需求，应去哪里；
- 我修改了接口，应更新哪些知识；
- 我想查看当前工作，应打开什么；
- 我想检查知识库，应执行什么。

根机器入口只保存机器可读取的类型目录和模板索引，不复制中文说明正文。

检查器验证：

- 每种知识类型都有使用契约；
- 使用契约包含必需章节；
- 每个实体能定位到对应使用契约；
- 模板字段与 Schema 一致；
- 目录和命名规则没有冲突。

优点：

- 使用者不需要了解仓库内部实现就能找到说明；
- 每类文档的规则集中维护，不在所有实体中重复；
- 使用说明本身是 Obsidian 可链接的知识节点；
- 模板、Schema 和说明可以进行一致性检查；
- 既适合人阅读，也适合 Agent 按规则操作。

限制：

- 每种知识类型需要维护一份使用契约；
- 必须检查 README、模板和 Schema 是否同步；
- 类型很多时根导航需要保持简洁。

### 33.4 方案 B：所有使用说明集中在一份总手册

知识库只提供一份《知识库使用手册》，集中说明所有文档类型、路径、字段和操作规则。

优点：

- 文件数量少；
- 可以一次性阅读全部规则；
- 全局规则集中。

限制：

- 文档会越来越长；
- 使用者进入具体目录时看不到就近说明；
- 修改某类模板时容易忘记同步总手册；
- Obsidian 中所有类型都指向同一个大文件，图谱和定位不清晰；
- Agent 需要读取大量无关内容。

### 33.5 方案 C：只在模板字段中写注释

不提供独立使用说明。每个模板通过占位文字或 YAML 注释解释字段如何填写。

优点：

- 规则离填写位置最近；
- 不需要额外说明文档；
- 模板看起来可以直接使用。

限制：

- 创建实体后注释可能被删除；
- 难以完整说明生命周期、关系和责任边界；
- 所有模板会重复大量规则；
- 规则更新时需要修改多份模板；
- 普通使用者无法在创建文档前了解整体用法。

### 33.6 已批准方案

采用方案 A：

- 根 README 负责“从哪里开始”；
- 类型目录 README 负责“这一类文档怎么用”；
- 模板负责“当前这一份怎么填写”；
- Schema 负责“机器允许什么格式”；
- 检查器负责验证四者一致；
- 面向用户的说明全部中文优先，机器字段首次出现时附中文解释。

### 33.7 已确认决策

已批准方案 A：

- 根 README 提供面向任务的总入口；
- 每类知识目录 README 提供该类文档的中文使用契约；
- 实体模板只保留简短填写指引和使用契约链接；
- Schema 定义机器格式；
- 检查器验证根导航、使用契约、模板和 Schema 的一致性。

## 34. 议题十三：Plugin 安装、更新与 Skill 承载

### 34.1 状态

已批准（机器状态 `approved`）

### 34.2 术语和范围

- **Skill（技能）**：Agent 实际读取和执行的知识库工作流程，当前机器名称为 `context-atlas`。
- **Plugin（插件）**：用户发现、安装、更新和卸载的完整软件包。插件可以包含一个或多个 Skill，也可以按需包含 MCP 服务或界面。
- **Skill-only Plugin（仅技能插件）**：插件中只有 Skill 和必要资源，不包含远程服务、登录或界面。Context Atlas 第一阶段适合这种最小形态。
- **目标项目知识库**：Skill 在业务项目中创建和维护的 `doc-<项目名>/`，不属于已安装 Skill 本体。

当前阶段只支持能够安装并执行 Skill 的 Agent。不再承诺为完全不支持 Skill 的 Agent 提供等价入口。

安装或更新插件不能覆盖目标项目知识库。插件版本和目标项目版本相互独立：升级插件只升级工作流程、模板和检查器；目标知识库是否迁移必须单独分析并经用户确认。

### 34.3 方案 A：仓库本身就是一个仅技能插件（推荐）

在仓库根目录增加插件清单，复用现有 `skills/context-atlas/`，不复制 Skill：

```text
context-atlas/
├── .codex-plugin/
│   └── plugin.json
├── .claude-plugin/
│   ├── plugin.json
│   └── marketplace.json
├── skills/
│   └── context-atlas/
│       ├── SKILL.md
│       ├── agents/openai.yaml
│       ├── references/
│       └── assets/
├── README.md
└── CHANGELOG.md
```

用户安装的是 `context-atlas` 插件，Agent 执行的是插件内的 `context-atlas` Skill。Codex 读取 `.codex-plugin/plugin.json`；Claude Code 读取 `.claude-plugin/plugin.json`，并通过 `.claude-plugin/marketplace.json` 提供仓库级市场入口。两个平台共享同一个 `skills/context-atlas/`，不能复制第二份 `SKILL.md`、模板或规则。开发阶段分别通过两个平台的本地插件方式测试；稳定后再决定是否提交公共插件目录。插件名称、目录名和 Skill 名统一使用小写连字符格式 `context-atlas`。

这仍然属于方案 A，而不是方案 B：方案 A 允许同一个插件仓库提供多个平台必需的清单；只有复制插件目录、Skill 内容或业务规则，才属于多平台外壳方案。

用户操作只保留五项：

1. **安装**：从插件目录或代码仓库安装 `context-atlas` 插件。
2. **检查版本**：显示当前插件版本和可用版本。
3. **更新**：通过平台原生插件机制重新安装或升级插件。
4. **卸载**：只移除插件本体，不删除任何目标项目知识库。
5. **验证**：在新会话中验证插件可发现、Skill 可触发、模板与检查规则完整。

两个 `plugin.json` 分别保存平台要求的插件名称、版本和说明，并保持名称、版本、描述等共同字段一致。代码仓库版本标签继续作为可追溯发布点；是否支持固定到历史版本，取决于所用插件来源和平台能力，不自建一套复杂更新器。

更新时遵循：

- 不自动修改任何目标项目知识库；
- 如果新版兼容当前知识库格式，只提示可以继续使用；
- 如果需要迁移，先生成迁移提案，列出受影响文件和不可逆变化；
- 用户批准后才更新目标知识库；
- 不因插件卸载而删除目标项目知识库；
- 不承诺支持无法安装该插件或无法执行其 Skill 的 Agent。

优点：

- 仓库、插件和 Skill 各只有一份，不存在同步副本；
- 安装、更新、卸载和发现交给平台原生插件机制；
- 当前仓库已有 `skills/context-atlas/`，改造范围最小；
- Codex 与 Claude Code 可以共享同一份 Skill、引用资料、模板和检查器；
- 安装更新与目标知识库迁移明确分离；
- 未来可以在同一插件中增加相关 Skill、检查脚本或 MCP 服务。

限制：

- 两个平台的插件清单不能合并为同一个文件，需要分别校验；
- 公共插件目录发布需要额外审核，开发阶段先使用本地插件市场；
- 平台不提供历史版本固定时，只能通过代码仓库标签保留可追溯来源。

### 34.4 方案 B：核心 Skill 加多个平台插件外壳

继续把 `skills/context-atlas/` 作为独立发布物，同时为 Codex、其他支持 Skill 的 Agent 分别建立插件外壳。各外壳只引用或构建同一份 Skill 内容。

优点：

- 覆盖更多 Agent；
- 每个平台可以使用自己的安装入口；
- 核心知识规范仍可保持一致。

限制：

- 需要构建脚本或发布流程保证各外壳内容一致；
- 每个平台都需要独立安装、更新和行为测试；
- 分发与兼容矩阵会明显增加维护成本；
- 当前用户已明确不再支持不能适配 Skill 的 Agent，因此第一阶段收益有限。

### 34.5 方案 C：保持独立 Skill，不做插件

只发布 `skills/context-atlas/`。用户通过 Skill 安装器或手工复制安装，不增加 `.codex-plugin/plugin.json`。

优点：

- 实现最简单；
- 适合个人工作流快速迭代；
- 不绑定插件平台。

限制：

- 安装、更新、卸载和发现体验不统一；
- 团队分发能力弱；
- 将来增加多个相关 Skill 或工具时仍要迁移到插件；
- 不符合“把稳定能力作为可安装产品分发”的方向。

### 34.6 已批准方案

已批准修订后的方案 A：

- 把 Context Atlas 仓库直接做成一个 `context-atlas` 插件；
- 为 Codex 和 Claude Code 分别维护必要的插件清单，但共同字段必须同步；
- 两个平台共享唯一 `skills/context-atlas/`，禁止复制 Skill 正文和资源；
- 插件第一阶段只包含现有 `context-atlas` Skill，不增加 MCP 服务和界面；
- 插件是用户安装和更新的单位，Skill 是插件内执行工作的单位；
- 使用平台原生插件机制，不自建复杂安装器和自动更新服务；
- 插件版本使用语义化版本，代码仓库标签保存可追溯发布点；
- 插件更新与目标知识库迁移严格分离；
- 后续新增能力优先作为同一插件中的相关 Skill，只有确需受控外部工具时才增加 MCP。

### 34.7 已确认决策

已批准方案 A：仓库本身作为正式 `context-atlas` Plugin；现有 `context-atlas` Skill 原地成为插件内能力；第一阶段为仅技能插件；Codex 与 Claude Code 分别使用自己的插件清单并共享唯一 Skill 内容；安装、更新和卸载使用各平台原生插件机制；插件更新不自动迁移或删除目标项目知识库。

### 34.8 跨平台兼容边界

- **支持的是同一份能力，不是同一种插件清单。** Codex 与 Claude Code 的清单目录和市场格式不同，不能假设一个平台会读取另一个平台的清单。
- **Skill 使用共同子集。** 当前 `SKILL.md` 的 `name`、`description`、Markdown 正文和相对引用可以作为双方共享基础；新增平台专属字段前必须验证另一平台能否忽略该字段。
- **平台专属能力隔离。** 如果将来增加只适用于某个平台的钩子、Agent 或配置，必须放在平台专属目录或清单中，不能改变共享知识规范的含义。
- **分别验收。** 每次插件发布至少验证 Codex 安装、更新、触发和卸载，以及 Claude Code 安装、更新、命名空间触发和卸载。
- **兼容声明以实测为准。** 只有通过对应版本真实安装和代表性任务验证的平台，才能列入正式支持清单。

### 34.9 多 Agent 分发模型

采用“一个核心、多个薄适配、分别安装”的结构：

```text
context-atlas/
├── skills/context-atlas/          # 唯一核心 Skill
├── .codex-plugin/                 # Codex 分发清单
├── .claude-plugin/                # Claude Code 分发清单与市场入口
├── adapters/                      # 后续平台确有专属文件时才建立
│   ├── qoder/
│   └── trae/
└── docs/                          # 统一使用、更新和兼容说明
```

规则如下：

1. `skills/context-atlas/` 是唯一权威能力来源，所有平台读取或安装这一份内容。
2. 平台适配层只保存安装清单、路径映射、平台专属元数据和必要启动说明，不复制模板、Schema、引用资料或工作流程正文。
3. 每个平台使用自己的原生安装和更新方式；用户同时使用多个 Agent 时，需要分别安装，但它们来自同一个 Context Atlas 版本。
4. 平台专属适配失败不能改变核心 Skill；只能修复该平台适配层或暂时降低该平台支持状态。
5. 第一版必须完成 Codex 与 Claude Code 的真实安装、更新、触发、卸载和代表性知识库任务验收。
6. Qoder、Trae 等后续平台先进入候选或适配状态，完成相同验收后才能声明正式支持。

### 34.10 参考项目与取舍

#### Superpowers

Superpowers 维护一套可组合技能，但针对 Claude Code、Codex、Cursor、Gemini CLI 等不同 Agent 分别提供原生安装入口，并明确多 Agent 用户需要分别安装。Context Atlas 采纳其“核心技能共享、安装入口按平台区分”的方式。

来源：[Superpowers 仓库与安装说明](https://github.com/obra/superpowers)

#### OpenSpec

OpenSpec 通过一个全局安装包提供统一核心能力，再由 `openspec init` 和 `openspec update` 为已配置的 Agent 初始化或刷新命令及技能文件。Context Atlas 采纳其“核心版本统一、平台文件可刷新”的思想，但第一阶段不照搬全局 CLI，也不让安装器自动改写目标知识库。

来源：[OpenSpec 仓库](https://github.com/Fission-AI/OpenSpec)、[OpenSpec 安装与更新说明](https://openspec.dev/docs/installation)

#### Qoder 与 Trae

Qoder 已支持标准 `SKILL.md`、用户级与项目级 Skill，以及从 GitHub 安装第三方 Skill；Trae 已宣布支持从 `.agents/skills` 加载 Skill。因此两者适合作为后续平台适配目标，但在实际安装与代表性任务验收完成前，不声明正式支持。

来源：[Qoder Skills 官方说明](https://docs.qoder.com/extensions/skills)、[Trae 更新记录](https://www.trae.ai/changelog)

### 34.11 已确认的平台范围

- 第一版正式支持：Codex、Claude Code。
- 后续优先候选：Qoder、Trae。
- 其他 Agent：只有支持安装或适配 Skill，并通过 Context Atlas 验收契约后才纳入。
- 不支持 Skill、不能读取 Skill 资源或无法完成必要文件操作的 Agent，不在支持范围内。

### 34.12 已确认的平台状态

平台支持状态统一分为三档：

1. **正式支持**：已经提供可重复的安装和更新方式，通过当前版本规定的完整验收，并在用户文档中提供使用说明。第一版目标为 Codex、Claude Code。
2. **适配中**：已经开始编写或测试平台清单、路径映射或安装说明，但尚未完成全部验收。可以邀请测试，不能在首页或发布说明中宣称正式支持。
3. **候选支持**：已确认该平台具备 Skill 能力或存在合理适配路径，但还没有进入实际适配。当前优先候选为 Qoder、Trae。

状态管理规则：

- 仅创建平台目录、清单或安装说明，不能自动把状态提升为正式支持；
- 平台从候选支持进入适配中，需要有明确适配负责人或当前任务；
- 平台从适配中进入正式支持，必须保存对应版本的验收证据；
- 已正式支持的平台如果因平台升级导致核心流程失效，应降为适配中，并在兼容说明中标明受影响版本；
- 平台状态只表示 Context Atlas 在该 Agent 上的兼容程度，不表示该 Agent 产品本身的质量或成熟度。

## 35. 议题十四：正式支持平台的验收强度

### 35.1 状态

已批准（机器状态 `approved`）

### 35.2 方案 A：统一完整验收契约（推荐）

每个正式支持平台都必须在受控测试项目中完成同一组结果验收：

1. 安装插件或 Skill；
2. Agent 能发现并正确触发 `context-atlas`；
3. Skill 能读取自己的引用资料、模板、Schema 和检查器；
4. 能按确认流程初始化一份测试知识库；
5. 能读取、更新并验证已有测试知识库；
6. 能执行插件或 Skill 更新，并显示版本变化；
7. 卸载只移除插件或 Skill，不删除测试项目知识库；
8. 核心结果、确认边界和安全约束在各平台一致。

平台命令和界面可以不同，但验收结果必须一致。验收记录必须写明 Agent 名称、Agent 版本、Context Atlas 版本、操作系统、执行步骤和结果证据。

优点：

- “正式支持”含义明确且可信；
- 能发现平台虽然可以安装、但无法读取资源或正确执行流程的问题；
- 后续增加 Qoder、Trae 时可以复用同一准入标准；
- 平台升级后可以准确判断是否需要降级支持状态。

限制：

- 每次正式发布需要在所有正式支持平台分别执行验收；
- 跨平台测试成本高于简单冒烟测试。

### 35.3 方案 B：只验证安装、发现和触发

只要平台可以安装 `context-atlas`，并能触发 Skill，就标记为正式支持。初始化、更新、验证和卸载保护不做每个平台的完整测试。

优点：

- 验收速度快；
- 新平台可以较快进入支持列表。

限制：

- 无法证明完整知识库工作流可用；
- 可能在读取资源、执行检查器或保护已有知识库时失败；
- “正式支持”容易变成只代表可以安装。

### 35.4 方案 C：依据文档推断或用户反馈声明支持

只要平台官方说明支持 `SKILL.md`，或者社区用户报告可用，就标记为正式支持，不由 Context Atlas 项目维护者重复验收。

优点：

- 项目自身测试成本最低；
- 可以快速列出大量兼容平台。

限制：

- 缺少可复现证据；
- 平台版本、操作系统和安装方式差异可能被忽略；
- 用户反馈无法替代当前版本的发布验收；
- 不符合本项目“验证通过不等于内容正确、声明必须有证据”的原则。

### 35.5 已批准方案

采用方案 A。第一版分别对 Codex 和 Claude Code 执行完整验收；Qoder、Trae 等后续平台只有完成同一套结果验收后，才能从适配中提升为正式支持。

### 35.6 已确认决策

已批准方案 A：所有正式支持平台使用统一的完整验收契约；平台安装命令可以不同，但知识库初始化、读取、更新、验证、升级和卸载保护结果必须一致，并保存版本化验收证据。

## 36. 议题十五：Skill 数量与命名规范

### 36.1 状态

已批准（机器状态 `approved`）

### 36.2 当前仓库事实

当前仓库只提供一个公开 Skill：

```text
skills/context-atlas/SKILL.md
```

该 Skill 在内部根据用户请求选择初始化、查看、解释、更新、迁移或验证流程，并按需读取 `references/`。初始化、更新和验证目前是同一个产品能力的操作分支，不是独立安装产品。

### 36.3 方案 A：第一版保持一个完整 Skill（推荐）

插件名、Skill 目录名和 Skill 元数据名称统一为 `context-atlas`。初始化、查看、更新、迁移、影响分析和验证继续作为 Skill 内部操作，由入口 Skill 根据用户意图选择对应引用资料。

命名规则：

- 中文产品名：`脉络地图`；首次出现时写作“脉络地图（Context Atlas）”；
- 插件机器名：`context-atlas`；
- 核心 Skill 机器名：`context-atlas`；
- 机器名只使用小写英文字母、数字和连字符，不使用空格、下划线或中文；
- Codex、Claude Code 等平台适配清单都使用相同产品机器名，不创建 `context-atlas-codex`、`context-atlas-claude` 等平台分叉名称；
- Python 文件和模块继续遵守 Python 的下划线命名习惯，但这不属于 Skill 命名；
- `references/` 中的流程文档不是 Skill，不注册独立名称。

只有同时满足以下条件，未来才允许拆出新 Skill：

1. 它能被用户独立描述和触发；
2. 它有独立输入、输出和成功标准；
3. 它不需要复制核心 Skill 的大量规则；
4. 它可以独立测试和发布兼容说明；
5. 拆分能明显降低上下文加载或触发冲突，而不是只为了目录看起来整齐。

优点：

- 与当前仓库结构一致，改造最小；
- 用户只需理解和安装一个能力；
- 避免初始化、更新、迁移、验证等 Skill 描述相互重叠导致误触发；
- 所有平台共享同一个稳定名称；
- 引用资料可以按需加载，不需要通过拆 Skill 控制上下文。

限制：

- 主 `SKILL.md` 必须保持简洁，只负责路由和共同边界；
- 操作继续增加时，需要严格控制入口文件长度。

### 36.4 方案 B：按操作拆分多个 Skills

拆成类似以下多个公开 Skill：

```text
context-atlas-initialize
context-atlas-inspect
context-atlas-update
context-atlas-migrate
context-atlas-validate
```

优点：

- 每个 Skill 的用途比较单一；
- 可以分别触发和测试；
- 单个入口文件较短。

限制：

- 多个 Skill 会重复安全边界、来源规则和确认流程；
- “更新、迁移、验证”经常同时发生，Agent 可能选择错误或重复触发；
- 用户需要理解多个近似名称；
- 不同平台的命名空间显示可能不同；
- 当前规模不足以证明拆分收益大于维护成本。

### 36.5 方案 C：一个主 Skill 加多个可公开调用的子 Skill

保留 `context-atlas` 作为总入口，同时公开 `context-atlas-validate`、`context-atlas-migrate` 等少量专业 Skill。主 Skill 可以引导用户使用子 Skill。

优点：

- 保留统一入口；
- 高频或复杂操作可以独立演进；
- 将来可以按需要逐步拆分。

限制：

- 主 Skill 与子 Skill 的职责容易重叠；
- 不同 Agent 是否支持 Skill 之间稳定调用，需要逐个平台验证；
- 用户可能不知道应该调用总入口还是子入口；
- 第一版会增加不必要的触发和验收组合。

### 36.6 已批准方案

采用方案 A。第一版只发布一个 `context-atlas` Skill，把它设计成简短路由入口；详细流程继续放在中文 `references/` 中按需读取。未来只有出现经过证据证明的独立工作流时，再单独评审是否拆分，不预先占用名称。

### 36.7 已确认决策

已批准方案 A：第一版只发布一个机器名为 `context-atlas` 的完整 Skill；插件和各平台适配统一使用同一机器名；初始化、更新、迁移、验证等保留为内部操作，不拆成多个公开 Skills。

## 37. 议题十六：已批准规则由什么机制保证

### 37.1 状态

已批准（机器状态 `approved`）

### 37.2 问题说明

前面批准的规则既包含文件格式，也包含操作流程、跨文件关系、业务判断和发布验收。把全部规则写入 `SKILL.md` 并不能可靠保证执行：Agent 可能漏读、误解或在上下文压缩后遗忘；同时，Schema 和检查器也无法判断所有业务语义是否正确。

因此需要明确每类规则的唯一权威位置和执行保障，避免同一规则在 Skill、模板、Schema 和说明文档中维护多份互相冲突的正文。

### 37.3 方案 A：规则分层承载，每条规则只有一个权威来源（推荐）

为每条正式规则分配稳定规则编号，例如 `RULE-REL-001`、`RULE-DB-003`。规则正文只在一份中文规范文档中定义，其他载体通过规则编号和文件引用执行或验证该规则，不复制完整规则正文。

| 规则内容 | 权威或执行载体 | 能保证什么 | 不能保证什么 |
| --- | --- | --- | --- |
| 中文业务含义、适用范围、例外 | 规范文档 | 人和 Agent 能统一理解规则 | 无法仅靠文字阻止错误文件 |
| Agent 阅读顺序、提问、Proposal、确认和写入流程 | Skill 及其引用资料 | 约束 Agent 的工作步骤 | 不能证明最终业务内容真实 |
| 字段、类型、必填项、枚举值、状态值 | JSON Schema | 自动发现格式和值域错误 | 不能判断业务描述是否合理 |
| 新建文档的默认结构和填写提示 | 模板 | 降低创建错误概率 | 模板本身不能作为规则权威正文 |
| 文件链接、知识项 ID、关系类型、反向影响、逻辑外键等跨文件规则 | 确定性检查器 | 自动发现可计算的不一致 | 不能裁决不确定的业务影响 |
| 插件安装、升级、卸载和跨 Agent 一致性 | 平台验收用例 | 证明指定版本在指定平台实际可用 | 不能替代每个项目的业务验收 |
| 需求是否正确、字段含义是否真实、影响是否可接受 | 来源引用加人工确认 | 保证正式事实有责任人确认 | 不能由 Agent 或检查器自动决定 |

具体规则映射如下：

- `rel_<type>` 和 Obsidian 文件链接：规范文档定义含义，Schema 限制字段形态，检查器验证目标文件、锚点、知识项 ID 和关系合法性，模板提供示例，Skill 在写入前执行检查。
- 数据库字段含义和值域：表模板提供填写位置，Schema 要求必要字段，检查器验证值域结构和逻辑外键链接，业务负责人确认真实含义。
- 文档变化影响分析：规范文档定义关系和影响等级，检查器生成“必须处理、人工复核、提示信息”，Skill 组织用户确认，不能自动改写关联文件。
- 项目版本和变更封存：规范定义最小版本字段，模板提供变更记录结构，检查器验证版本引用，Skill 在用户发版操作中执行封存步骤。
- 所有正式知识必须有来源：Schema 要求来源字段或来源关系，检查器验证引用存在，人工确认来源是否可信且足以支持结论。

为避免规则分叉，还要建立一份规则目录，至少记录：

```yaml
- id: RULE-REL-001
  name_zh: 关系必须引用目标文件和知识项
  authority: "[[规范/关系与引用#RULE-REL-001|RULE-REL-001]]"
  enforced_by:
    - schema
    - validator
    - acceptance
```

规则目录只保存索引和执行映射，不复制规则正文。Schema、检查器错误信息、模板说明和验收用例都必须能追溯到规则编号及权威文档。

插件打包时，根仓库中的权威规范、模板、Schema 和检查器生成或复制为发布包；发布包是不可手工维护的产物，不能与根仓库再形成第二套权威内容。

优点：

- 不依赖 Agent 单纯“记住”所有规则；
- 人类规则、机器格式、跨文件检查和业务确认各司其职；
- 每个错误都能追溯到具体规则及中文说明；
- 更新规则时可以判断需要同步修改哪些 Schema、模板、检查器和验收用例；
- 适用于 Codex、Claude Code 及后续 Agent，不依赖某个平台的提示行为。

限制：

- 必须维护规则编号和规则目录；
- 规则变化时需要执行覆盖检查，确认所有执行载体已经同步；
- 仍有一部分业务语义只能人工确认，无法完全自动化。

### 37.4 方案 B：所有规则都写进 Skill

把文档格式、关系规则、数据库约束、更新流程和验收标准全部写入 `SKILL.md` 或其 `references/`，主要依靠 Agent 按说明执行。

优点：

- 文件集中，初期编写简单；
- Agent 阅读后可以直接执行；
- 不必建设规则目录和映射。

限制：

- 无法确定性检查 Agent 是否漏掉规则；
- Skill 会越来越长，上下文消耗和遗忘风险持续增加；
- 不同 Agent 对同一说明可能产生不同执行结果；
- 规则变更后无法自动发现 Schema、模板或检查器没有同步；
- 不适合承担数据库值域、关系链接等严格结构约束。

### 37.5 方案 C：规则全部交给检查器

Skill 只负责调用检查器，所有要求尽量编码进 Python 检查器，文档和模板只作为辅助说明。

优点：

- 可计算规则执行稳定；
- 不同 Agent 得到相同检查结果；
- 适合持续集成环境。

限制：

- 业务含义、来源可信度、影响可接受性无法可靠编码；
- 检查器会演变成复杂规则引擎；
- 用户难以理解错误背后的业务原因；
- 容易错误地把“结构通过”当成“内容正确”。

### 37.6 已批准方案

采用方案 A。Skill 只负责识别任务、按需读取规则、组织确认、调用模板和检查器；它不是全部规则的唯一存储位置。能机器判断的规则必须由 Schema 或检查器验证，不能机器判断的业务语义必须保留来源并由人确认。

### 37.7 已确认决策

已批准方案 A：每条正式规则只有一个带稳定编号和文件引用的中文权威来源；Skill、Schema、模板、检查器和验收用例按职责引用并落实该规则；发布包由权威源生成，不允许人工维护第二套规则。

## 38. 议题十七：规则变化后的同步发现机制

### 38.1 状态

已批准（机器状态 `approved`）

### 38.2 目标

当一条权威规则发生变化时，系统需要回答：

- 哪些 Skill 流程引用了该规则；
- 哪些 Schema、模板和检查器实现了该规则；
- 哪些平台验收和知识库样例验证了该规则；
- 哪些文件必须修改，哪些只需要人工复核；
- 如何证明所有影响已经处理，而不是依赖 Agent 全仓猜测。

### 38.3 方案 A：使用方声明规则引用，检查器生成反向索引（推荐）

每个使用规则的载体主动声明自己遵循哪些规则：

- Markdown 文档在 YAML 文档头部使用带文件路径的 Obsidian 内部链接，例如：

```yaml
rel_conforms_to:
  - "[[规范/关系与引用#RULE-REL-001|RULE-REL-001]]"
```

- JSON Schema 使用允许的扩展字段记录规则编号和权威文件路径；
- 检查器规则、模板清单和验收用例使用各自格式记录规则编号；
- 平台适配清单不复制规则正文，只声明其实现或验证的规则编号。

检查器扫描这些正向引用，生成“规则编号 → 所有使用方”的反向索引。反向索引是生成结果，不手工维护，也不成为第二份权威关系。

规则变化时执行：

1. 根据 Git 差异识别变化的规则编号；
2. 通过反向索引列出所有使用方；
3. 根据使用方类型生成“必须处理、需要人工复核、提示信息”；
4. 把清单写入当前变更集；
5. 每个使用方记录已修改、不需要修改及理由，或者保留未处理状态；
6. 检查器验证规则编号存在、文件链接有效、所有必须处理项都有结果；
7. 人工确认后才能关闭该规则变化。

例如 `RULE-REL-001` 从“只引用知识项 ID”改为“必须同时引用目标文件和知识项 ID”时，反向索引应至少找到关系 Schema、文档模板、链接检查器、迁移说明和跨平台验收用例。

优点：

- 关系从实际使用方出发，符合基础规范被上层实现引用的方向；
- Obsidian 能展示 Markdown 使用方到规则文档的文件关系；
- 不需要在规则文档中手工维护反向消费者列表；
- 影响结果可以重复计算和验证；
- 新增使用方时必须主动声明规则，否则覆盖检查可以报告缺失。

限制：

- 不同文件格式需要约定各自的规则引用字段；
- 首次需要为现有 Schema、模板、检查器和验收补充规则编号；
- 正文语义变化仍可能需要人工补充影响判断。

### 38.4 方案 B：在规则目录中手工列出全部使用方

每条规则的目录项直接维护 `used_by`，列出 Skill、Schema、模板、检查器和验收文件。

优点：

- 打开规则目录即可看到全部使用方；
- 影响查询简单，不需要扫描所有文件。

限制：

- 新增使用方时容易忘记修改规则目录；
- 规则目录变成手工维护的反向关系清单；
- 与“使用方引用基础规则、基础规则不反向维护上层文件”的方向冲突；
- 文件移动时集中清单容易失效。

### 38.5 方案 C：每次由 Agent 全仓搜索和推断

规则变化后，让 Agent 搜索相同字段名、关键词和相关代码，自行推断需要同步的文件，不建立明确规则编号和引用索引。

优点：

- 不需要增加结构字段；
- 对尚未建模的隐含关系有一定发现能力。

限制：

- 结果依赖 Agent、模型和当前上下文；
- 关键词变化或间接实现容易漏检；
- 无法证明已经覆盖全部已知使用方；
- 不适合作为正式规则变更的唯一保障。

### 38.6 已批准方案

采用方案 A。确定性规则引用负责已知影响的完整发现，Agent 全仓分析只作为补充，用于发现尚未登记的潜在关系；Agent 推测不能替代规则编号、文件引用和反向索引。

### 38.7 已确认决策

已批准方案 A：由 Skill、Schema、模板、检查器和验收等使用方主动引用权威规则；检查器生成反向索引；规则变化时自动形成影响清单并进入变更集，所有必须处理项得到结果后才能关闭。

## 39. 议题十八：知识来源、文档关系与质检引用

### 39.1 状态

已批准（机器状态 `approved`）

### 39.2 必须区分的三种引用

1. **知识来源引用**：证明“这项事实从哪里获得”，例如用户确认、仓库文件、命令输出、已有文档或外部文档。
2. **文档关系引用**：表达“两个知识项是什么业务关系”，例如实现需求、暴露接口、读取数据表或验证功能。
3. **质检引用**：证明“检查结果根据哪条规则、检查了哪个文件和知识项”。

三者都必须能定位文件和知识项，但不能混用同一个无语义的 `references` 字段。

### 39.3 方案 A：来源实体加分层精确引用（推荐）

每个可追溯来源建立稳定 `SRC-*` 知识项。来源可以一项一文件，也可以在来源汇总文件中按标题聚合；无论如何，引用必须包含来源文件路径、可选锚点和来源编号。

文档头部至少使用：

```yaml
rel_supported_by:
  - "[[00-项目总览/知识来源#SRC-001|SRC-001]]"
```

来源知识项记录：

- 来源编号和中文名称；
- 来源类型；
- 仓库文件路径、提交标识、外部网址或用户确认上下文；
- 获取或确认时间；
- 支撑的内容摘要；
- 当前是否有效；
- 是否包含冲突、敏感信息或访问限制。

精度规则：

- 整份文档来自同一批来源时，在 YAML 文档头部统一引用；
- 某个章节、表格行或关键结论使用不同来源时，在对应位置增加来源内部链接；
- 数值、枚举值、接口字段、数据库字段含义、业务规则和决策结论必须尽量引用到具体来源项，不能只引用一个宽泛的项目首页；
- 外部网址统一保存在来源知识项中，业务文档引用来源文件，不在大量业务文档中重复维护同一网址；
- `ai_inference`（AI 推测）可以作为待确认来源记录，但不能单独支撑 `approved`（已批准）事实。

文档业务关系继续使用已经批准的 `rel_<type>`：

```yaml
rel_implements:
  - "[[01-需求/订单需求|REQ-001]]"
rel_reads:
  - "[[02-架构与契约/数据库/数据表/订单表|TABLE-ORDER-001]]"
```

质检结果必须至少包含：

```yaml
rule: "[[规范/关系与引用#RULE-REL-001|RULE-REL-001]]"
target: "[[01-功能/FUNC-ORDER-001-创建订单|FUNC-ORDER-001]]"
location: "rel_implements[0]"
result: failed
message_zh: 目标知识项编号与目标文件中的编号不一致
```

检查器验证：

- 来源链接目标文件和来源编号存在；
- `approved` 文档至少有一个有效、非纯 AI 推测的来源；
- 文档关系符合关系类型允许的源和目标；
- 质检结果同时引用规则和被检查对象；
- 链接移动后知识项编号保持稳定，索引可以重新定位；
- 来源失效或冲突时，所有引用它的知识项进入人工复核清单。

优点：

- Obsidian 图谱能看到业务文档到来源文件、关联文档和规则文档的不同边；
- 相同外部网址或仓库证据只维护一份；
- 质检错误有规则依据和准确目标；
- 来源变化可以通过反向索引触发影响分析；
- 能区分真实证据、业务关系和检查依据。

限制：

- 来源项需要稳定编号和基本维护；
- 细粒度结论可能需要在正文中增加局部来源链接；
- 当前仅保存 `sources: [SRC-001]` 的文档需要迁移为带文件链接的关系。

### 39.4 方案 B：只在文档头部列来源编号

继续使用：

```yaml
sources: [SRC-001, SRC-002]
```

优点：

- 格式简单；
- 当前模板迁移较少。

限制：

- Obsidian 无法形成到来源文件的图谱边；
- 不知道 `SRC-001` 位于哪个文件；
- 无法区分某个结论具体由哪个来源支持；
- 与已批准的“关系必须包含文件链接和知识项编号”不一致。

### 39.5 方案 C：在正文直接粘贴网址或路径

每处事实后直接写外部网址、仓库路径或自然语言来源，不建立 `SRC-*` 来源知识项。

优点：

- 阅读当前位置即可看到原始地址；
- 不需要维护来源目录。

限制：

- 相同网址会在多份文件重复；
- 来源变化时无法可靠找到全部引用；
- 用户陈述、命令输出和提交证据难以统一表达；
- 无法稳定管理来源冲突、失效和敏感性；
- 不利于生成一致的 Obsidian 图谱。

### 39.6 已批准方案

采用方案 A。`SRC-*` 来源实体负责证据，`rel_<type>` 负责业务关系，质检结果必须同时引用规则和被检查对象。现有裸 `sources` 编号不再作为最终格式，迁移时转换为带来源文件路径和来源编号的 `rel_supported_by`。

### 39.7 已确认决策

已批准方案 A：所有正式知识通过带文件路径和来源编号的 `rel_supported_by` 引用来源实体；业务关系继续使用类型化文件链接；质检结果必须引用规则文件和目标文件；纯 AI 推测不能单独支撑已批准事实。

## 40. 议题十九：受控业务关系目录

### 40.1 状态

已批准（机器状态 `approved`）

### 40.2 关系目录必须回答的问题

每种关系必须集中定义：

- 机器字段名和中文名称；
- 它表达的业务含义；
- 允许哪些知识类型作为起点；
- 允许哪些知识类型作为目标；
- 链接方向；
- 是否需要正文补充字段映射或说明；
- 目标变化后，哪些起点知识进入必须处理或人工复核；
- 是否允许同一目标重复出现；
- 是否已经启用、保留还是弃用。

### 40.3 方案 A：有限核心关系加受控扩展（推荐）

第一版只启用能够明确解释和检查的核心关系：

| 机器字段 | 中文含义 | 允许的起点 | 允许的目标 | 主要变化影响 |
| --- | --- | --- | --- | --- |
| `rel_supported_by` | 由该来源支持 | 正式知识项 | 来源 `SRC-*` | 来源失效或冲突时，起点进入人工复核 |
| `rel_conforms_to` | 遵循该规则 | 文档、模板、Schema、检查器、验收 | 规则 `RULE-*` | 规则变化时，使用方进入必须处理或人工复核 |
| `rel_implements` | 实现该需求 | 功能、业务规则 | 需求 `REQ-*` | 需求范围变化时，实现方进入人工复核；删除或替代时必须处理 |
| `rel_exposes` | 对外提供该契约 | 功能、模块 | 接口、事件 | 接口或事件发生破坏性变化时，提供方及消费者必须处理 |
| `rel_reads` | 读取该数据 | 功能、模块、处理任务 | 数据表、数据资产 | 字段删除、类型或值域收紧时，读取方必须处理 |
| `rel_writes` | 写入该数据 | 功能、模块、处理任务 | 数据表、数据资产 | 必填、默认值、类型或值域变化时，写入方必须处理 |
| `rel_depends_on` | 运行或业务上依赖 | 功能、模块、接口、任务 | 模块、外部依赖或依赖能力 | 目标不可用、删除或发生不兼容变化时必须处理 |
| `rel_verified_by` | 由该验收项证明 | 需求、功能、业务规则、接口 | 验收项 `AC-*` | 被验证对象变化时，验收项必须复核；验收失效时对象不能视为已验证 |
| `rel_changes` | 本次变更涉及 | 变更集 | 任意被修改知识项 | 目标变化必须纳入该变更集的影响和验收范围 |
| `rel_supersedes` | 替代旧知识 | 新知识项 | 同类型旧知识项 | 旧知识转为已替代，所有旧引用进入迁移或复核 |
| `rel_logical_parent` | 逻辑上引用主表 | 子表 | 主表 | 主表键变化时子表必须处理；正文必须记录子字段到主字段映射 |

说明：外部依赖的详细能力模型当前仍然暂缓；`rel_depends_on` 关系名可以保留，但第一阶段不要求建立完整外部依赖能力清单。

关系字段统一使用小写英文和下划线，并以 `rel_` 开头。每个值必须是包含目标文件路径、可选锚点和目标知识项编号的 Obsidian 内部链接。

关系只保存一个权威方向。例如功能通过 `rel_reads` 指向数据表；数据表不手工保存“被哪些功能读取”。反向关系由检查器生成，因此 Obsidian 图谱仍能显示文件之间存在连接，影响分析也能找到所有读取方。

影响等级不直接固定在字段名上，而由“关系类型 + 目标变化类型”共同决定。例如：

```yaml
relation: rel_reads
target_change:
  field_description_changed: informational
  nullable_tightened: required
  enum_value_removed: required
  field_added_optional: review_required
```

其中：

- `required`：必须处理；
- `review_required`：需要人工复核；
- `informational`：提示信息。

新增关系类型必须经过规则变更提案，说明为什么现有关系无法表达、允许的起点和目标、影响传播规则、迁移方式以及验收用例。未经登记的 `rel_*` 字段由检查器报错。

优点：

- 同一关系在不同 Agent 和项目中含义一致；
- 可以确定性检查错误方向和错误知识类型；
- 影响分析有明确规则，而不是只靠关键词推测；
- 防止关系名称无限增长或出现近义重复；
- 保留未来受控扩展能力。

限制：

- 第一版需要维护关系目录和影响规则；
- 新业务关系不能随意新增字段，需要先评审；
- 部分关系的业务真实性仍需人工确认。

### 40.4 方案 B：允许每个项目自定义任意 `rel_*`

项目可以自由创建 `rel_calls`、`rel_uses`、`rel_links` 等关系，只要求值是合法文件链接。

优点：

- 灵活，项目可以快速表达特殊关系；
- 不需要等待核心规范增加关系类型。

限制：

- 不同项目会为相同含义创建不同名称；
- 无法统一判断合法起点、目标和影响；
- 检查器只能检查链接存在，不能检查业务方向；
- 后续迁移和跨项目分析困难。

### 40.5 方案 C：只保留一个通用 `rel_related_to`

所有文档关系统一写入 `rel_related_to`，具体含义在正文解释。

优点：

- 字段最少；
- 几乎所有关系都能连接；
- Obsidian 可以形成基础图谱。

限制：

- 无法区分实现、读、写、依赖和验证；
- 无法根据关系类型进行影响分析；
- Agent 必须重复阅读正文猜测关系含义；
- 不能满足用户提出的明确关系类型要求。

### 40.6 已批准方案

采用方案 A。第一版采用有限核心关系，关系目录是机器校验和中文说明的共同依据；允许未来扩展，但新增关系必须通过规则变更流程，不能由项目临时发明近义字段。

### 40.7 已确认决策

已批准方案 A：建立受控核心关系目录；每种关系明确中文含义、合法起点、合法目标、权威方向和按变化类型计算的影响等级；禁止未登记的 `rel_*` 字段；反向关系由检查器生成而不手工保存。

## 41. 议题二十：聚合文件内知识项的精确定位

### 41.1 状态

已批准（机器状态 `approved`）

### 41.2 背景

一项一个文件时，链接目标文件即可精确定位。一个文件聚合多个术语、来源或短小规则时，关系还必须定位文件内的具体知识项。Obsidian 支持标题链接 `#标题` 和块链接 `#^块编号`；块引用是 Obsidian 专用语法，不属于标准 Markdown。

来源：[Obsidian 内部链接官方说明](https://obsidian.md/help/links)

### 41.3 方案 A：知识项编号作为标题前缀，使用标题锚点（推荐）

聚合文件中的每个知识项使用“稳定编号 + 中文名称”作为标题：

```markdown
## SRC-001 用户确认订单状态

## RULE-REL-001 关系必须引用目标文件和知识项
```

链接写为：

```yaml
rel_supported_by:
  - "[[00-项目总览/知识来源#SRC-001 用户确认订单状态|SRC-001]]"
rel_conforms_to:
  - "[[规范/关系与引用#RULE-REL-001 关系必须引用目标文件和知识项|RULE-REL-001]]"
```

稳定性规则：

- 编号是知识身份，不允许修改或复用；
- 中文名称可以修改，但修改标题时必须由工具同步更新所有内部链接；
- 检查器以显示编号和目标标题编号为准，不把整段标题文字当成身份；
- 聚合文件拆分时保持编号不变，并由迁移工具更新文件路径；
- 标题层级可以变化，但同一文件内知识项编号必须唯一；
- 聚合文件只用于短小实体；需求、功能、接口、数据表等高引用对象仍默认一项一个文件。

优点：

- 人类打开 Markdown 即可看到编号和中文名称；
- 标题链接属于常见 Markdown 锚点概念，跨工具兼容性优于 Obsidian 块引用；
- Obsidian 可以自动补全标题链接；
- 编号和中文名称同时提供身份与可读性；
- 标题本身形成清晰文档结构。

限制：

- 中文名称改变时链接中的标题文字需要同步更新；
- 不适合精确引用表格中的单独一行；
- 不同 Markdown 工具对中文标题锚点转换可能略有差异，Context Atlas 检查器必须按原始标题解析，不能依赖外部工具生成的 URL 锚点。

### 41.4 方案 B：使用稳定 Obsidian 块编号

在知识项末尾增加与知识项编号对应的块编号：

```markdown
## 用户确认订单状态

相关来源内容。

^SRC-001
```

链接写为：

```yaml
rel_supported_by:
  - "[[00-项目总览/知识来源#^SRC-001|SRC-001]]"
```

优点：

- 中文标题变化不影响块编号；
- 可以定位普通段落或列表项；
- 标识符只包含英文字母、数字和连字符，便于机器解析。

限制：

- 块引用是 Obsidian 专用格式，在普通 Markdown 工具中不能正常跳转；
- 块编号放在正文中较突兀；
- 结构化块、表格和引用存在定位限制；
- 知识项标题与块编号分离，人工检查时更容易错配。

### 41.5 方案 C：标题锚点和块编号同时维护

每个聚合知识项既用带编号标题，也增加相同编号的块标识；链接可以按使用场景选择标题或块。

优点：

- 同时具备标题可读性和块编号稳定性；
- 可以兼容更多精确定位场景。

限制：

- 同一知识项存在两个定位方式；
- 引用格式不统一，检查器和迁移逻辑更复杂；
- 标题编号和块编号可能不一致；
- 不符合“每种关系只有一个权威表示”的原则。

### 41.6 已批准方案

采用方案 A。知识项稳定性由 `SRC-*`、`RULE-*` 等编号保证，不依赖中文标题永远不变；工具负责在标题或文件移动时同步链接。只有确实需要引用无法成为知识项标题的单段内容时，才允许普通文档使用块链接，但块链接不得作为正式知识项的默认身份。

### 41.7 已确认决策

已批准方案 A：聚合文件中的正式知识项统一使用“稳定编号 + 中文名称”的标题，并通过标题锚点精确引用；块编号只作为特殊段落引用的例外，不作为正式知识项默认定位方式。

## 42. 议题二十一：项目版本与知识库格式兼容

### 42.1 状态

已批准（机器状态 `approved`）

### 42.2 已确认边界

- 使用者日常只看到目标项目版本，例如 `3.4.0`；
- 知识库随目标项目同仓、同提交、同标签演进；
- Context Atlas 不建设复杂发布系统；
- 插件升级不能自动迁移目标项目知识库；
- 仍然需要一种机器可读方式，判断新版插件能否读取旧知识库格式。

### 42.3 方案 A：一个内部格式主版本，用户界面默认隐藏（推荐）

目标知识库根 `knowledge-base.yaml` 只增加一个内部字段：

```yaml
project_version: 3.4.0
format_version: 2
```

含义：

- `project_version`：业务项目当前版本，面向用户展示；
- `format_version`：Context Atlas 文档结构的主版本，只供插件、检查器和迁移判断使用，日常文档不反复展示。

插件清单记录：

```yaml
plugin_version: 1.6.0
reads_format_versions: [1, 2]
creates_format_version: 2
```

这里的中文含义是：插件版本 `1.6.0` 可以读取格式 1 和 2；新建知识库使用格式 2。

兼容规则：

1. 插件能读取当前 `format_version`：正常工作，不要求迁移。
2. 插件能读取但新建格式更高：提示存在可选迁移，不自动修改。
3. 插件不能读取当前格式：停止正式写入，只允许只读检查和生成迁移提案。
4. 格式变化只有在旧结构无法继续正确表达或验证时才提升主版本；新增可选字段、说明改进和向后兼容的检查规则不提升。
5. 迁移必须创建变更集，列出文件变化、规则变化和影响；用户确认后执行。
6. 迁移完成后只更新 `format_version`，不因此修改 `project_version`；项目版本是否变化由业务项目发版决定。
7. 插件版本、项目版本和格式版本不做数学绑定，不要求三者数字一致。

日常显示示例：

```text
项目版本：3.4.0
知识库格式：兼容
```

只有发生不兼容或用户查看诊断信息时，才显示具体格式版本数字。

优点：

- 用户仍然只需理解项目版本；
- 插件可以确定性判断是否安全读写；
- 只有一个内部兼容数字，复杂度最低；
- 插件升级与知识库迁移保持分离；
- 可以支持旧知识库逐步升级。

限制：

- 仍需维护格式迁移规则；
- 插件发布时必须验证其声明的格式兼容范围；
- 主版本内的向后兼容边界需要规则约束。

### 42.4 方案 B：完全不记录知识库格式版本

只保存项目版本。插件读取知识库后，通过文件结构和字段猜测属于哪种格式。

优点：

- 字段最少；
- 用户完全看不到额外版本。

限制：

- 无法可靠判断旧知识库能否被新版插件安全修改；
- 格式识别逻辑复杂且可能误判；
- 迁移失败时难以诊断；
- 插件更新与知识库结构变化失去明确边界。

### 42.5 方案 C：插件、规范、Schema 和模板分别版本化

分别记录插件版本、规范版本、Schema 版本、模板版本、检查器版本和项目版本，并维护兼容矩阵。

优点：

- 每个组件变化都能精确追踪；
- 适合大型平台和独立发布的多个组件。

限制：

- 版本数量和兼容矩阵复杂；
- 用户和维护者都需要理解多个版本；
- 与已经批准的简化版本方向冲突；
- 当前项目没有足够独立发布组件证明这种复杂度必要。

### 42.6 已批准方案

采用方案 A。保留项目版本作为唯一用户业务版本，只增加一个默认隐藏的 `format_version` 供机器判断兼容；不再单独引入规范版本、Schema 版本和模板版本。

### 42.7 已确认决策

已批准方案 A：知识库只增加一个内部整数 `format_version`；插件声明可读取的格式范围和新建格式；不兼容时停止写入并生成迁移提案；迁移格式不自动改变项目版本。

## 43. 议题二十二：接口和功能的变化控制

### 43.1 状态

已批准（机器状态 `approved`）

### 43.2 目标与边界

接口和功能需要知道“发生了什么变化、是否会影响使用方”，但不应为每份文档再维护一套独立语义化版本号。项目版本仍是唯一业务发布版本；知识项继续使用 `introduced_in`、`last_changed_in`、`deprecated_in` 记录它与项目版本的关系。

### 43.3 方案 A：变化等级加兼容规则，不设置独立知识项版本（推荐）

每次变更集为受影响知识项记录变化等级：

| 等级 | 中文含义 | 处理要求 |
| --- | --- | --- |
| `documentation_only` | 仅文档变化 | 不改变业务行为，只做结构和引用检查 |
| `compatible` | 向后兼容变化 | 原有使用方式仍然有效，相关方收到提示或人工复核 |
| `breaking` | 破坏性变化 | 原有使用方可能失效，必须完成影响处理和迁移说明 |
| `deprecated` | 已弃用 | 仍可使用但不建议新增使用，必须记录替代项或退出条件 |
| `removed` | 已移除 | 旧能力不再可用，所有有效引用必须迁移、关闭或解释保留原因 |

#### 接口的破坏性变化

以下变化默认标记 `breaking`：

- 删除或重命名接口、操作、事件、请求字段或响应字段；
- 新增必填请求字段且没有兼容默认值；
- 字段类型、格式、单位或语义不兼容变化；
- 枚举值删除、重命名或含义改变；
- 可空改为不可空；
- 成功状态、错误码、鉴权、权限或幂等语义发生不兼容变化；
- 同步改异步，或消息投递、顺序和重试保证降低；
- 限流、超时或容量约束收紧并可能使原使用方式失败。

以下变化通常为 `compatible`，但仍需结合消费者检查：

- 新增可选请求字段；
- 新增响应字段且消费者约定忽略未知字段；
- 新增接口或枚举值，且现有消费者能够处理未知值；
- 放宽允许值、长度、容量或权限限制；
- 修正文档但不改变已实现语义。

如果无法证明消费者能够兼容，不能自动判为 `compatible`，统一进入人工复核。

#### 功能的破坏性变化

以下变化默认标记 `breaking`：

- 删除、关闭或重命名用户可见能力；
- 前置条件、权限、默认行为或关键业务规则发生不兼容变化；
- 输出结果、状态流转、失败处理或数据保存语义改变；
- 已批准范围缩小；
- 用户原有操作路径不再可用；
- 依赖功能、接口或数据结构发生破坏性变化，且没有兼容层。

新增可选能力、放宽约束或不影响既有行为的增强通常为 `compatible`。纯文字改进为 `documentation_only`。

#### 记录方式

变化等级只记录在变更集中，不反复修改知识项的独立版本号：

```yaml
id: CHG-2026-018
project_version: 3.4.0
changes:
  - target: "[[02-架构与契约/接口/API-ORDER-001-创建订单|API-ORDER-001]]"
    change_level: breaking
    summary_zh: 删除请求字段 customer_type 的枚举值 TEMPORARY
```

知识项本身只更新：

```yaml
last_changed_in: 3.4.0
```

影响处理：

1. 检查器读取变化等级和受控关系目录；
2. 通过反向索引找到接口消费者、功能、验收项、读写表和相关规则；
3. `breaking`、`removed` 默认产生“必须处理”；
4. `compatible` 默认产生提示或人工复核；
5. `documentation_only` 只执行结构、来源和链接检查；
6. 检查器继续查找受影响对象关联的验收项及其当前版本验收证据；
7. 证据失败时确认存在可观察影响，证据过期或缺失时标记“影响未验证”，证据通过时只能证明已覆盖场景通过；
8. Agent 可以建议变化等级，但责任人必须确认 `breaking` 与 `compatible` 的最终分类；
9. Context Atlas 不阻止项目发版，只报告未处理影响和未验证影响。

优点：

- 用户不需要理解每个接口和功能的独立版本号；
- 与项目版本和变更集自然结合；
- 可以直接驱动影响分析；
- 可以结合验收证据确认变化是否已经影响被覆盖的业务场景；
- 接口、功能、规则和数据变化使用统一语言；
- 保留人工判断边界，避免检查器误判业务兼容性。

限制：

- 需要建立变化分类规则；
- 部分兼容性依赖消费者行为，必须人工复核；
- 无法单凭一个数字比较两个知识项版本。

### 43.4 方案 B：每个接口和功能独立使用语义化版本

每个接口、功能、表或规则都维护类似 `2.3.1` 的独立版本，根据变化大小分别升级主版本、次版本或修订版本。

优点：

- 单个知识项版本变化直观；
- 可以对外公布明确接口版本；
- 适合真正独立部署和长期并行维护的公共 API。

限制：

- 一个复杂需求可能同时修改大量知识项版本；
- 用户需要维护项目版本和多套知识项版本；
- 版本数字本身不能说明具体影响；
- 与当前简化版本决策冲突；
- 内部功能和数据库表通常没有独立发布生命周期。

如果业务项目本身已经提供公开 API 版本，例如 URL `/v2/` 或协议版本字段，知识库应如实记录该外部事实；这不意味着 Context Atlas 再为所有知识项创建版本。

### 43.5 方案 C：只在变更记录中写自然语言，不分类

变更集只描述“修改了接口”或“调整了功能”，不使用统一变化等级。

优点：

- 记录最自由；
- 不需要维护分类规则。

限制：

- 检查器无法确定影响强度；
- 不同作者对同类变化的表述不一致；
- 无法自动筛选破坏性变化；
- 容易遗漏消费者迁移和验收更新。

### 43.6 已批准方案

采用方案 A。用变化等级表达兼容性，用项目版本表达发布时间，用变更集组织影响处理；不为内部接口、功能、表和规则增加独立版本体系。业务影响判断同时使用关系反向索引和验收证据，具体职责在议题二十三中确认。

### 43.7 已确认决策

已批准方案 A：接口和功能不维护独立版本号；变化在变更集中分类为仅文档、兼容、破坏性、弃用或移除；分类结合关系反向索引驱动影响分析；已存在的公共 API 版本作为项目事实如实记录。

## 44. 议题二十三：需求、功能、任务包、验收项与验收证据

### 44.1 状态

已批准（机器状态 `approved`）

### 44.2 各知识类型的作用

| 类型 | 回答的问题 | 生命周期 | 不负责什么 |
| --- | --- | --- | --- |
| 需求 `REQ-*` | 为什么做、需要达到什么业务结果 | 可跨多个项目版本长期存在 | 不描述具体代码修改步骤 |
| 功能 `FUNC-*` | 系统稳定提供什么能力 | 随产品能力长期维护 | 不等于某一次开发任务 |
| 变更集 `CHG-*` | 这一次交付修改哪些知识项 | 随一次实际变更创建，完成后封存 | 不替代长期需求和功能文档 |
| 任务包 `TASK-*` | 本次由谁修改什么、允许改哪里、怎么执行 | 一次实施过程 | 不定义长期业务事实，不证明结果已通过 |
| 验收项 `AC-*` | 满足什么条件才算正确 | 跟随被验证的需求、功能、接口或规则 | 不保存某次执行产生的实际结果 |
| 验收证据 `EVID-*` | 在什么环境、版本和时间执行后实际发生了什么 | 每次有效验收产生一份，可随版本封存 | 不能自行定义验收标准，也不能证明未覆盖场景无影响 |

一个完整链路示例：

```text
需求 REQ-ORDER-001
  ← 功能 FUNC-ORDER-001 通过 rel_implements 实现
  ← 变更集 CHG-2026-018 通过 rel_changes 纳入本次修改
  ← 任务包 TASK-ORDER-018-01 负责具体实施
  ← 验收项 AC-ORDER-001 定义必须证明的业务条件
  ← 验收证据 EVID-ORDER-001-20260813 记录本次实际结果
```

其中任务包是“怎么做”，验收项是“怎样才算正确”，验收证据是“实际执行结果”。三者不能合并成同一种文档。

### 44.3 方案 A：关系影响与验收证据双通道（推荐）

第一通道是**结构影响分析**：

- 根据变化等级、`rel_implements`、`rel_reads`、`rel_writes`、`rel_verified_by` 等关系找出可能受影响的业务对象；
- 它在执行测试之前就能工作；
- 它回答“哪些地方可能受影响、哪些必须检查”。

第二通道是**证据验证**：

- 验收项通过新增受控关系 `rel_evidenced_by` 指向验收证据；
- 验收证据必须记录目标项目版本、执行环境、执行时间、步骤、预期结果、实际结果、结论和原始证据位置；
- 它回答“已覆盖的业务场景在本次版本上实际是否通过”。

示例：

```yaml
# 功能文件
rel_verified_by:
  - "[[03-实施与验收/验收项/AC-ORDER-001-创建订单成功|AC-ORDER-001]]"

# 验收项文件
rel_evidenced_by:
  - "[[03-实施与验收/验收证据/EVID-ORDER-001-20260813|EVID-ORDER-001-20260813]]"
```

影响结论至少区分：

| 关系分析 | 验收证据 | 结论 |
| --- | --- | --- |
| 发现候选影响 | 相关证据失败 | 已确认存在业务影响 |
| 发现候选影响 | 相关证据通过且仍适用于当前版本 | 已覆盖场景未发现回归，其他场景仍按关系分析处理 |
| 发现候选影响 | 证据缺失、过期或环境不适用 | 影响尚未验证，必须补充或人工处理 |
| 未发现已登记关系 | 证据失败 | 既存在业务影响，也说明关系或验收覆盖可能缺失 |
| 未发现已登记关系 | 无证据 | 不能据此得出“无业务影响”，只能报告未发现已登记影响 |

关键边界：

- 验收通过不能推翻明确的破坏性变化；例如删除接口字段，即使旧测试未覆盖该字段而全部通过，仍然是必须处理；
- 验收失败可以确认被覆盖场景已经受到影响；
- 验收缺失或过期意味着未知，不等于无影响；
- 验收证据必须与当前项目版本、目标对象和验收项匹配；旧版本证据不能直接证明新版本；
- 人工业务验收、自动化测试、命令输出、截图或报告都可以成为证据，但必须记录来源和适用范围；
- 检查器验证证据链完整性，不判断业务人员的人工验收是否真实正确。

受控关系目录增加：

| 机器字段 | 中文含义 | 起点 | 目标 | 方向 |
| --- | --- | --- | --- | --- |
| `rel_evidenced_by` | 由该次实际证据证明 | 验收项 `AC-*` | 验收证据 `EVID-*` | 验收项指向证据 |
| `rel_executes` | 执行该变更集中的工作 | 任务包 `TASK-*` | 变更集 `CHG-*` | 任务包指向变更集 |

优点：

- 影响分析既有事前的结构推导，也有事后的实际证据；
- 可以清楚区分“可能受影响”“已确认受影响”和“已覆盖场景通过”；
- 需求、功能、实施和验收职责清晰；
- 证据过期、缺失或覆盖不足可以被明确报告；
- 不会把测试通过误当成所有业务均无影响。

限制：

- 需要为验收项和证据建立稳定编号及引用；
- 每个重要变更需要更新或重新执行相关验收；
- 仍然无法自动证明所有潜在业务场景都已覆盖。

### 44.4 方案 B：只依据验收证据判断业务影响

如果相关测试或人工验收通过，就认为没有业务影响；失败则认为有影响。

优点：

- 结论直接；
- 容易理解和执行。

限制：

- 未覆盖的字段、场景和消费者不会出现在证据中；
- 旧证据可能已经过期；
- 可能把“测试没测到”错误解释成“没有影响”；
- 无法在测试执行前列出完整候选影响。

### 44.5 方案 C：只使用关系影响分析，不关联验收证据

根据文档关系和变化规则生成影响清单，但不读取验收项和执行证据。

优点：

- 结构简单；
- 不依赖测试环境和执行结果。

限制：

- 只能报告可能影响，无法知道实际场景是否已经回归；
- 不能识别验收覆盖缺失或证据过期；
- 任务完成与业务验证之间缺少闭环。

### 44.6 已批准方案

采用方案 A。关系分析负责发现候选影响和强制处理范围，验收证据负责确认被覆盖业务场景的实际结果；两者互相补充，任何一方都不能单独得出“完全没有业务影响”。

### 44.7 已确认决策

已批准方案 A：保留需求、功能、变更集、任务包、验收项和验收证据的独立职责；新增 `rel_evidenced_by` 和 `rel_executes`；业务影响由关系分析与当前版本验收证据共同判断，验收通过只能证明已覆盖场景，不能推翻明确破坏性变化或证明所有业务无影响。

## 45. 议题二十四：现有知识库迁移到新规范

### 45.1 状态

已批准（机器状态 `approved`）

### 45.2 迁移目标与边界

迁移用于解决“旧知识表达逻辑无法被最新版规则直接理解”的情况，不是每次规则或插件升级都必须执行的固定流程。

用户补充的边界是：最新版规则应优先直接读取已有知识库；如果新旧规则表达的业务逻辑没有变化，应直接接收旧知识，不要求改写文件；只有知识表达逻辑发生变化时，才需要把旧逻辑转换为新逻辑。

第一版不建设复杂迁移平台，只提供兼容判断和必要的格式转换。

### 45.3 方案 A：兼容读取优先，逻辑变化时按版本转换（推荐）

插件读取知识库时，按照以下顺序处理：

1. **可以直接理解**：最新版规则能够正确解释旧字段、旧目录或旧链接，而且业务含义没有变化，直接读取和接收，不修改文件，也不启动迁移。
2. **可以等价转换**：新旧表达方式不同，但存在明确的一对一转换规则，由对应格式版本转换器生成新表达。例如把能够唯一定位的旧 `sources` 转换为 `rel_supported_by` 文件链接。
3. **无法等价转换**：旧知识缺少新版必需的业务含义，或者存在一对多、编号冲突、目标不唯一等歧义，只报告具体问题并请用户确认，不自动猜测。

兼容和转换规则按内部格式版本维护，例如：

```text
格式 1 → 最新格式：执行字段和关系等价转换
格式 2 → 最新格式：可以直接读取，无需迁移
格式 3 → 最新格式：已经是当前格式
```

这里的编号只是示意，实际规则以插件声明的 `reads_format_versions` 和版本转换器为准。

最小保护规则：

- 只读兼容不生成迁移提案，不改文件；
- 等价转换先显示转换摘要，用户确认后统一写入；
- 转换后运行新规则检查，通过后更新内部 `format_version`；
- 不能等价转换的内容保持原样并列出待确认项；
- 不复制整套知识库，不长期维护新旧两份权威文档；
- 使用现有 Git 历史恢复，不另建迁移备份系统；
- 插件更新和项目知识库迁移分别执行，安装或更新插件时不得自动开始迁移；
- 迁移自身只更新内部 `format_version`，不自动更新 `project_version`；
- 不自动提交、暂存或丢弃用户修改。

优点：

- 绝大多数兼容升级不产生迁移工作；
- 只有知识表达逻辑真正变化时才执行转换；
- 转换器职责单一，可以分别测试每个旧格式到新格式的转换结果；
- 旧知识不需要长期保持多套读写逻辑；
- 与内部 `format_version` 以及插件兼容范围相匹配。

限制：

- 每次非兼容逻辑变化都要提供对应转换规则；
- 无法等价转换的业务语义仍需人工确认；
- 插件需要测试直接读取和转换两条路径。

### 45.4 方案 B：任何格式差异都统一转换到最新版

只要旧知识库的 `format_version` 不是最新版，就执行一次完整转换，即使新规则仍然能够无损读取旧格式。

优点：

- 所有知识库最终具有完全相同的物理格式；
- 检查器只需要重点验证最新格式。

限制：

- 纯字段、目录或说明变化也会制造大量无意义差异；
- 用户频繁遇到迁移提示；
- 与“逻辑没有变化就直接接收”的目标冲突；
- 转换和审阅成本更高。

### 45.5 方案 C：永久兼容所有旧逻辑，只读不转换

插件为每一种历史格式长期保留独立读取和写入逻辑，不转换已有知识库。

优点：

- 不需要修改旧知识库；
- 用户不会经历迁移写入过程。

限制：

- 插件需要永久维护所有历史业务逻辑；
- 新逻辑可能无法用旧结构完整表达；
- 读取、更新、检查和影响分析都要维护多套分支；
- 时间越久复杂度越高，也更容易出现不同格式结果不一致。

### 45.6 已批准方案

采用方案 A。最新版规则先尝试直接读取；能保持原有业务含义就直接接收，只有表达逻辑不兼容时才调用明确的版本转换器。这样保留必要兼容能力，同时不把迁移设计成独立复杂系统。

### 45.7 已确认决策

已批准方案 A：最新版规则优先直接读取旧知识库；业务逻辑没有变化时直接接收，不迁移；只有新旧知识表达逻辑不兼容时才按格式版本执行等价转换；无法等价转换的内容交给用户确认。

## 46. 议题二十五：Codex 与 Claude Code 插件清单

### 46.1 状态

已批准（机器状态 `approved`）

### 46.2 已确认的平台事实

- Codex 插件清单位于 `.codex-plugin/plugin.json`；
- Claude Code 插件清单位于 `.claude-plugin/plugin.json`；
- 两个平台都支持 `name`、`version`、`description`、`author`、`homepage`、`repository`、`license`、`keywords` 和 `skills` 等基础字段；
- Codex 使用 `interface` 对象表达安装界面信息；Claude Code 的 `displayName` 等字段位于自己的清单结构中，并且还支持 Codex 第一版不需要的命令、代理、钩子等能力；
- 两个平台均可从插件根目录的 `skills/` 加载 Skill，因此可以共享 `skills/context-atlas/`；
- 平台清单、插件市场目录和 Context Atlas 自身的知识库格式兼容声明是三类不同文件，不能混为一种清单。

### 46.3 方案 A：两个薄平台清单，共享字段强制一致（推荐）

仓库根目录保留两个平台入口：

```text
.codex-plugin/plugin.json
.claude-plugin/plugin.json
skills/context-atlas/SKILL.md
compatibility.json
```

安装后的效果：

```text
安装前                         安装后
已有插件 A                     已有插件 A
已有插件 B          →          已有插件 B
                               context-atlas
```

安装器和平台适配必须遵守以下已批准规则：

1. 已有其他插件、市场条目和用户配置全部保留，Context Atlas 作为新插件追加；
2. 同一来源、同一版本的 Context Atlas 已存在时不重复安装，只报告“已安装”；
3. 同一来源的旧版本 Context Atlas 可以更新为新版本，但只更新本插件；
4. 同名 `context-atlas` 来自不同市场或仓库时视为来源冲突，停止自动安装并展示来源和版本供用户选择；
5. 检测到以前单独安装的 `context-atlas` Skill 时先保留；插件完成安装和验证后，再由用户决定是否移除旧入口；
6. 不替换整个插件市场文件，只新增 Context Atlas 条目或更新已经确认属于 Context Atlas 的条目；
7. 插件安装、更新、停用和卸载都不得自动修改目标项目知识库。

两个平台清单共同维护且必须一致的发布字段：

| 字段 | 中文含义 | 规则 |
| --- | --- | --- |
| `name` | 插件机器名称 | 固定为 `context-atlas` |
| `version` | 插件发行版本 | 两份清单相同，并与插件发布标签一致 |
| `description` | 插件用途简介 | 中文优先，两份清单表达同一含义 |
| `author` | 作者或维护团队 | 两份清单相同 |
| `homepage` | 使用文档地址 | 两份清单相同 |
| `repository` | 源码仓库地址 | 两份清单相同 |
| `license` | 开源许可证 | 两份清单相同 |
| `keywords` | 检索关键词 | 两份清单相同 |
| `skills` | Skill 目录 | 都指向共享的 `./skills/` |

Codex 专属内容只写入 `.codex-plugin/plugin.json`：

- `interface.displayName`：界面显示名称；
- `interface.shortDescription`、`interface.longDescription`：安装界面说明；
- `interface.category`、`interface.capabilities`：分类和能力说明；
- 图标、品牌颜色和使用入口等 Codex 安装界面字段；
- 第一版是纯 Skill 插件，不声明不存在的 `mcpServers` 或 `apps`。

Claude Code 专属内容只写入 `.claude-plugin/plugin.json`：

- `displayName`：Claude Code 界面显示名称；
- 可选 `$schema`：供编辑器和校验器识别清单格式；
- 第一版不声明 `commands`、`agents`、`hooks`、`mcpServers`、`lspServers`、`dependencies` 等未使用能力；
- 默认安装后启用，因此不额外声明 `defaultEnabled`，除非未来产品行为改变。

Context Atlas 自己的兼容能力放在共享 `compatibility.json`，不塞入平台清单：

```json
{
  "reads_format_versions": [1, 2],
  "creates_format_version": 2
}
```

检查器执行以下一致性检查：

1. 两个清单的共同字段存在且一致；
2. `name` 与插件目录、Skill 命名和市场条目一致；
3. `version` 使用规范的三段版本号；
4. `skills` 均能定位到同一份 `skills/context-atlas/SKILL.md`；
5. 平台专属字段不得复制到另一个平台清单；
6. `compatibility.json` 中的格式范围有效，并与转换器和验收样例一致；
7. 分别运行 Codex 与 Claude Code 官方校验及完整安装验收。

优点：

- 两个平台都使用自己的正式格式，不依赖对未知字段的宽松处理；
- 核心 Skill、规范和兼容规则仍然只有一份；
- 平台差异清楚，后续增加 Qoder、Trae 时可以增加新的薄适配入口；
- 不需要建立复杂的清单生成系统。

限制：

- 发布版本时需要同步修改两份清单；
- 必须由检查器防止共同字段漂移；
- 新增平台专属能力时需要单独验收。

### 46.4 方案 B：两个平台使用完全相同内容的清单

在 `.codex-plugin/` 和 `.claude-plugin/` 下复制完全相同的最小 JSON，只使用两端字段交集。

优点：

- 两份清单内容容易比较；
- 不需要区分平台专属字段。

限制：

- 无法充分提供 Codex 的安装界面信息；
- 不能自然使用 Claude Code 的显示和平台能力字段；
- 未来任何一端收紧字段校验都可能造成兼容问题；
- 文件仍然有两份，并没有真正消除同步问题。

### 46.5 方案 C：只维护一份源清单，发布时生成两个平台清单

建立一个 Context Atlas 自定义的发布元数据文件，发布脚本据此生成 Codex 和 Claude Code 清单。

优点：

- 共同字段只有一个编辑来源；
- 多平台增加后可以统一生成；
- 大量平台时减少人工重复。

限制：

- 引入自定义生成器、模板和发布步骤；
- 开发仓库中的平台清单可能与源文件不同步；
- 用户从 Git 仓库直接安装前必须确保生成产物已经提交；
- 第一版只有两个平台，复杂度暂时没有足够收益。

### 46.6 已批准方案

采用方案 A。两个平台各自使用正式的薄清单，共同字段由检查器强制一致，平台差异只留在对应清单；核心 Skill 和知识格式兼容声明继续共享。若未来正式支持的平台明显增加，再评估是否升级为方案 C 的生成模式。

### 46.7 已确认决策

已批准方案 A：仓库同时提供 `.codex-plugin/plugin.json` 与 `.claude-plugin/plugin.json`；两者共享发布字段并由检查器保证一致，各自只保存平台专属字段；知识库格式兼容范围独立放在共享 `compatibility.json`，不混入平台清单。

## 47. 议题二十六：开发过程知识的主动捕获与自动入库

### 47.1 状态

已批准（机器状态 `approved`）

### 47.2 问题本质

Codex、Claude Code 或其他 Agent 在使用 Superpowers、OpenSpec 等插件进行需求讨论、设计、计划、调试和实现时，会产生四类内容：

| 内容位置 | 性质 | 默认能否成为正式知识 |
| --- | --- | --- |
| Agent 会话 | 临时上下文，可能包含用户决定和推测 | 不能直接成为正式知识，但用户明确决定必须被捕获 |
| `docs/superpowers/specs/` | 设计过程或已批准设计文档 | 可以作为来源；是否成为权威契约取决于用户确认 |
| `docs/superpowers/plans/` | 一次实施计划 | 可以支撑任务包，不自动成为长期业务事实 |
| `.superpowers/` | 临时执行、迁移审查或工具产物 | 默认只作执行证据，不自动提取为业务事实 |

这些文件位于目标项目仓库，不是 Superpowers 私有知识库。但 Context Atlas 当前没有持续检查这些信息并把重要变化带入项目知识库的触发机制，因此知识可能停留在会话或过程文件中。

“自动入库”必须区分两步：

1. **自动捕获候选**：防止知识丢失，可以由 Agent 主动创建待确认提案；
2. **正式知识入库**：改变项目知识基线，必须满足来源、关系、影响分析和用户确认规则。

### 47.3 方案 A：自动捕获为待确认提案，确认后正式入库（推荐）

Context Atlas Skill 作为知识捕获协调者。其他插件仍按自己的流程工作；Context Atlas 不拦截也不复制完整会话，而是在明确事件和检查点识别“知识候选”。

#### 自动触发时机

出现以下事件时，Agent 必须执行一次轻量知识检查：

1. **用户作出明确决定后**：例如“同意”“采用方案 A”“范围不包含某功能”“字段只能存 1、2、3”；
2. **需求或业务规则变化后**：新增、修改、删除需求、功能、流程、权限、状态、枚举或计算规则；
3. **契约变化后**：接口、事件、数据库表、字段值域、逻辑外键或数据来源变化；
4. **设计完成、实施计划生成前**：防止计划依赖尚未入库的决定；
5. **任务完成或准备交付前**：对代码、配置、迁移和文档差异进行一次知识同步检查；
6. **验收完成后**：把验收结果与当前版本证据关联；
7. **项目发版前或版本变更记录封存前**：检查本版本重要变化是否已经进入知识库；
8. **会话即将结束或上下文压缩前**：只捕获尚未处理的重要决定和冲突，避免重复写入。

#### 每次触发后的判断

```text
发现新信息
├── 与现有知识相同 → 不写入，只记录“无需更新”
├── 可验证的新事实 → 创建待确认提案
├── 用户明确决定 → 创建待确认提案，并标记确认来源
├── 与现有知识冲突 → 创建冲突提案，不覆盖原文
└── 只是推测或临时调试信息 → 不入正式知识；必要时记录为假设或执行证据
```

#### 候选保存方式

每次触发可以创建或更新一个轻量的知识提案 `PROP-*`，至少记录：

- 候选知识摘要；
- 建议更新的正式知识项和文件；
- 来源：用户陈述、仓库文件、命令输出或其他插件过程文件；
- 与现有知识的差异；
- 可能影响的关联文件；
- 未决问题和冲突；
- 捕获时间、Agent 和适用项目版本；
- 状态 `proposed`，不得自动标记为 `approved`。

同一会话或同一任务中的相关候选应合并到一个提案，避免每句话生成一个文件。重复内容根据目标知识项 ID 和内容摘要去重。

#### 正式入库方式

Agent 在自然检查点向用户展示一份简短摘要：

```text
发现 3 项知识变化：
1. 订单状态新增 3=已取消，建议更新 TABLE-ORDER 和 RULE-ORDER-002。
2. 创建订单接口新增可选字段 remark，建议标记为兼容变化。
3. 超时时间只是调试参数，不建议进入业务知识库。
```

用户可以一次回复“全部同意”“同意第 1、2 项”或提出修订。只有获确认的内容才更新正式知识文件、关系和影响记录；未确认内容继续保持提案，拒绝项关闭但保留必要审计信息。

#### 与其他插件的关系

- Superpowers、OpenSpec 等过程文件只是来源或执行载体，不成为第二套权威知识库；
- Context Atlas 提取知识项和引用，不复制整份会话或整份过程文档；
- 已批准且适合作为专业设计契约的文档可以由正式知识文件直接引用；
- 临时目录 `.superpowers/` 默认不扫描业务语义，只在验收或故障证据明确引用时使用；
- Context Atlas 不能保证作为后台进程永远自动运行，因此其 Skill 描述、知识库协作规则和任务完成检查必须共同声明这些触发点；支持钩子的平台以后可以增加提醒，但第一版不依赖钩子。

优点：

- 开发沟通中的关键决定不容易丢失；
- 不会把 AI 推测和临时调试内容直接污染正式知识库；
- 不依赖某一个开发流程插件；
- 用户可以批量确认，不要求每句话都打断开发；
- 能与来源引用、关系影响和验收证据形成闭环。

限制：

- 第一版依赖 Agent 遵守触发规则，不能做到操作系统级后台监听；
- 候选提案需要去重和定期处理；
- 会话即将异常中断时仍可能来不及捕获，因此重要决定后的即时触发不能只依赖会话结束。

### 47.4 方案 B：检测到知识变化就直接修改正式知识

Agent 在会话中发现需求、设计或代码变化后，立即更新正式知识文件，不创建提案，也不等待用户批量确认。

优点：

- 正式知识更新最快；
- 没有待确认队列。

限制：

- AI 可能把推测、临时方案或未获批准的内容写成事实；
- 与已经批准的来源和人工确认原则冲突；
- 开发中的反复尝试会造成知识库频繁抖动；
- 难以区分“代码当前行为”和“业务应该如此”。

### 47.5 方案 C：只在用户明确说“同步知识库”时处理

Context Atlas 不主动识别知识变化，只有用户明确要求时才回顾当前会话和文件并生成更新。

优点：

- 实现最简单；
- 不会产生多余提案；
- 用户完全控制入库时机。

限制：

- 用户容易忘记触发；
- 上下文压缩或新会话后可能无法完整恢复决定；
- 其他插件生成的设计和计划可能长期游离在正式知识库之外；
- 无法满足“主动让 AI 捕获知识”的目标。

### 47.6 已批准方案

采用方案 A。自动化负责“发现、摘要、去重和保存待确认候选”，人负责“批准业务含义”，确认后 Agent 才负责“更新正式知识、关系和影响记录”。这既能防止知识遗忘，也不破坏人工确认边界。

### 47.7 已确认决策

已批准方案 A：Context Atlas 在用户决定、需求/契约变化、计划前、任务完成、验收、发版和会话结束等检查点主动捕获知识；自动内容只进入 `proposed` 待确认提案，用户确认后才写入正式知识基线；其他插件产物只作为来源、契约或执行证据，不成为第二套权威知识库。

## 48. 议题二十七：多人协作的知识写入者与确认者追踪

### 48.1 状态

已批准（机器状态 `approved`）

### 48.2 问题本质

多人共同维护知识库时，“谁写入了内容”至少包含四种不同责任，不能混为一个作者字段：

| 责任 | 中文含义 | 可能主体 |
| --- | --- | --- |
| 内容提出者 | 谁提供、发现或发起了本次候选知识 | 开发人员或 Agent |
| 文件操作方 | 谁实际修改了知识文件 | 开发人员或 Agent |
| 内容确认者 | 谁批准候选内容进入正式知识基线 | 具有确认责任的人员 |
| Git 提交者 | 谁创建、提交或合并了 Git 变更 | 开发人员、代提交者或自动化账号 |

Git 的作者和提交者只能证明代码仓库中记录了谁执行提交，不能单独证明谁提出了业务知识、谁实际编辑文件或者谁批准了内容。尤其在 Agent 代写、他人代提交、代码评审合并和自动化账号提交时，四种身份可能完全不同。

### 48.3 方案 A：Git 自动发现候选身份，项目人员编号长期追踪（已批准）

项目知识库使用稳定的 `PERSON-*` 人员编号作为人员身份，不把可变的 Git 用户名或邮箱直接作为长期主键。固定入口 `doc-<项目名>/00-项目总览/协作人员.md` 维护人员编号、显示名称、所属团队、状态和已确认的 Git 身份别名。

每份正式知识文档只保存当前追踪所需的轻量字段：

```yaml
created_by: PERSON-001
last_changed_by: PERSON-002
last_confirmed_by: PERSON-003
last_changed_at: 2026-08-13
```

其中，`created_by` 和 `last_changed_by` 表示对知识内容负责的人员，不用来冒充实际文件编辑工具。每一次提案或变更集保存完整角色：

```yaml
proposal_id: PROP-20260813-001
proposed_by: PERSON-002
operated_by: AGENT-CODEX
confirmed_by: PERSON-003
git_commit: abc1234
```

`proposed_by` 允许使用人员编号或 Agent 编号，以表达知识是由开发人员提出，还是由 Agent 根据仓库证据主动发现；`operated_by` 如实记录实际写文件的人员或 Agent；`confirmed_by` 必须指向具有确认责任的 `PERSON-*`；`git_commit` 是可选的技术审计证据，不等价于业务确认。

#### Git 身份解析规则

1. Agent 可以读取 Git 的 `user.name`、`user.email`、提交作者和提交者信息，自动查找候选人员；
2. 匹配顺序为：已确认的项目人员映射、已确认的 Git 身份别名、尚未确认的新候选；
3. 首次发现的新 Git 身份必须请求用户确认是已有人员还是新人员，确认前不得自动建立正式身份映射；
4. 同一人员更换 Git 用户名或邮箱时，为原 `PERSON-*` 增加别名，不创建新的人员身份；
5. Git 用户名重名、邮箱变化、统一自动化账号或无法唯一匹配时，标记为 `PERSON-UNKNOWN` 并请求确认，Agent 不得猜测；
6. 邮箱属于个人信息，知识库默认不在普通文档展示完整邮箱；人员登记表优先保存不可逆邮箱摘要用于匹配，只有项目明确需要且允许时才保存完整邮箱；
7. Git 信息可以帮助自动填写，但不能覆盖用户已经确认的人员映射。

#### 历史和展示边界

- 单个知识文件不嵌入完整修改历史，避免文件膨胀和多人合并冲突；
- 提案和变更集记录逐次角色、原因、确认结果和关联提交；
- Git 保存文件级差异、作者、提交者和时间，作为补充技术证据；
- 人员离开项目后将状态改为 `inactive`，保留原编号和历史引用，不复用编号；
- Obsidian 可以通过文档中的 `PERSON-*` 引用关联协作人员文件，但人员关系不替代业务知识之间的 `rel_*` 关系。

优点：身份稳定，能够区分谁提出、谁代写、谁确认和谁提交；Git 信息仍可自动利用，同时避免把可变用户名、邮箱和提交人误当成唯一责任人。

限制：首次识别新人员需要一次人工确认；人员登记表和 Git 别名需要随团队变化维护。

### 48.4 方案 B：直接使用 Git 用户名或邮箱

把 Git 用户名或邮箱直接写入知识文档。该方案实现简单、可以完全自动填写，但身份可修改、可能重名、可能泄露个人信息，也无法可靠表达内容确认者，因此不采用。

### 48.5 方案 C：完全人工填写人员编号

不读取 Git，每次变更都由用户手工指定人员编号。该方案身份明确，但操作成本高且容易漏填，不能充分利用仓库已有信息，因此不采用。

### 48.6 已确认决策

已批准方案 A：Git 只负责自动发现、匹配候选身份和提供提交证据；知识库以稳定的 `PERSON-*` 编号追踪人员。首次匹配必须由用户确认；正式记录明确区分内容提出者、文件操作方、内容确认者和 Git 提交者；邮箱默认只保存不可逆摘要，不在普通知识文档中公开。

## 49. 议题二十八：知识治理与任务调度的边界

### 49.1 状态

已批准（机器状态 `approved`）

### 49.2 问题本质

Context Atlas 的职责是保存、关联和验证项目知识，不是项目管理系统或 Agent 任务调度器。任务可能由用户直接发起，也可能来自 Superpowers、OpenSpec、Issue 系统、Codex、Claude Code 或其他插件。知识库无法完整知道这些系统的当前任务，因此不能根据自己的 `CURRENT.md` 判断外部任务是否允许执行。

原设计中的“无 CURRENT 任务时停止”和“只能执行 ready 任务包”越过了知识治理边界，会错误阻止其他合法工作流。

### 49.3 方案 A：取消执行门禁，当前变化和任务包只作可选知识记录（已批准）

- 目标知识库不再强制要求 `03-实施与验收/CURRENT.md`；已有文件迁移时可以保留为兼容别名，但其内容不构成执行许可；
- 新模板使用可选的 `03-实施与验收/当前变更.md`，记录知识库当前已知的零个、一个或多个 `CHG-*`，不声明项目是否存在“可执行任务”；
- `TASK-*` 任务包是可选的实施知识，只在需要保存跨会话实施范围、执行约束、责任归属或验收命令时创建；
- 用户或其他插件可以在没有任务包、没有当前变更记录的情况下执行代码工作；
- Context Atlas 可以在执行前提供相关知识和影响提示，在执行后发现知识差异并生成提案，但不能因未登记任务而阻止代码任务；
- 正式知识库写入仍受提案、确认、来源、关系和验证规则约束。这是知识写入门禁，不是业务代码执行门禁；
- 检查器可以报告“代码变化尚未关联知识变更”或“已知变更缺少证据”，不能报告“任务禁止执行”。

### 49.4 任务包的准确职责

任务包回答“某次实施工作准备怎样完成”，可以记录：

- 外部任务来源及其引用，例如 Superpowers 计划、OpenSpec 变更、Issue 或用户指令；
- 本次实施目标和排除范围；
- 计划修改的代码或知识范围；
- 关联的 `REQ-*`、`FUNC-*`、`CHG-*`、接口、表、规则和 `AC-*`；
- 负责人、执行 Agent、风险、未知项和阻塞；
- 建议执行步骤、验证命令和预期证据；
- 完成状态和产生的 `EVID-*` 引用。

任务包不保存长期业务事实，不复制需求、功能或接口正文，不充当执行许可证，也不能证明任务已经正确完成。

创建时机采用按需规则：

1. 简单问答、只读分析、无长期知识影响的临时调试，不创建任务包；
2. 需求刚提出时，先形成 `PROP-*` 候选和必要的 `REQ-*`、`AC-*`，此时通常不急于创建任务包；
3. 进入具体实施且工作需要跨会话、多人协作、明确修改范围或复现验证时，创建或引用 `TASK-*`；
4. Superpowers、OpenSpec 等已经提供完整实施计划时，任务包只保存外部计划引用、知识关系和验收映射，不复制整份计划；
5. 实施完成后，任务包记录实际状态并关联证据；长期有效事实分别更新到需求、功能、接口、数据库和规则文档；
6. 对知识没有长期价值的实施细节不要求永久保存，任务包可以按版本归档。

### 49.5 一次需求的知识收纳链路

一次需求进入后，Context Atlas 按内容性质拆分，而不是把所有信息塞进任务包：

```text
用户提出需求
→ PROP-*：保存尚未确认的候选、来源、假设和冲突
→ REQ-*：确认后保存为什么做、业务目标和范围
→ AC-*：保存怎样才算满足需求
→ FUNC-* / RULE-* / API-* / TABLE-*：保存受影响的长期能力和契约
→ CHG-*：组织这一次交付实际改变的知识项和影响
→ TASK-*（按需）：记录某次实施怎样执行及外部计划引用
→ EVID-*：记录验收实际结果
→ 发版时：把本版本 CHG-* 和证据纳入简化变更记录
```

同一需求不一定产生所有类型：没有数据库变化就不创建或修改表文档；没有跨会话实施管理需要就不创建任务包；没有实际执行就不会提前生成验收证据。

### 49.6 已确认决策

已批准方案 A：Context Atlas 是项目知识治理系统，不是任务调度系统。取消 `CURRENT.md` 对外部任务的执行门禁；当前变更和任务包只作为可选、可追溯的实施知识。其他插件或用户任务可以独立执行，Context Atlas 只在项目知识读取、正式知识写入、影响分析和证据完整性范围内提供规则与检查。
