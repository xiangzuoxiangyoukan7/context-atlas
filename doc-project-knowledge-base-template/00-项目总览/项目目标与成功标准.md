# 项目目标与成功标准

## 背景

不同项目和不同 AI 工具经常重复解释需求、设计和边界，导致计划依据不一致、验收标准漂移。本模板把项目事实、设计决策和验收证据组织成可迁移的知识库。

## 目标

1. 为 frontend、Java、Python 等项目提供统一的知识表达结构。
2. 让 AI 在生成计划前取得精准、可追溯的上下文。
3. 让功能、架构、数据库和验收标准保持相互引用且可检查。
4. 让自动检查发现结构性问题，把内容正确性留给人工评审。

## 最终提供的能力

本项目最终交付的是一套可初始化、可持续维护、可版本化、可追溯、可供 AI 消费的项目知识库治理能力，而不是某一个业务项目的知识库。

能力由以下层次组成：

1. **通用知识模型**：统一表达项目目标、功能、架构、契约、数据库、原型、外部依赖、任务、ADR、验收和证据。
2. **文档模板与 Schema**：约束必填字段、状态、版本和跨文档关联关系。
3. **项目初始化模板**：为新项目生成一致的知识库入口和目录结构。
4. **AI 上下文 Skill / Plugin**：按统一入口恢复当前、已批准的项目上下文。
5. **结构与关联检查器**：检查字段、链接、状态、版本、关联和验收证据的完整性。
6. **项目类型 Profile**：在不改变核心规则的前提下增加 frontend、Java、Python 等技术栈约束。

具体项目知识库（例如 `doc-anjian-security-engineer`）是上述通用能力的应用产物和验证样例，不是本项目的最终产品边界。
## 成功标准

- 新项目可以从 `template/` 初始化自己的知识库。
- 技术栈 profile 只增加约束，不改变核心状态和验收规则。
- 检查器可以发现缺字段、坏链接、状态冲突、验收漏项和证据缺失。
- 任意支持的 AI 工具都能沿同一入口顺序恢复当前状态。
- 项目、功能、架构/契约、数据库表、原型和外部依赖都能明确当前有效版本。
- 目标、功能、设计、任务、验收和证据之间可以建立可追溯关系链。
- AI 可以基于知识库生成执行计划，但不能替项目责任人批准事实、设计或验收标准。
- 自动检查能够证明结构完整性；内容是否正确仍由项目责任人评审确认。
