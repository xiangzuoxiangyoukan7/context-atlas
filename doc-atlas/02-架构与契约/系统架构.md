# 系统架构

## 技术基线

| 技术 | 版本 | 使用目录或模块 | 项目用途 | 构建、测试与运行命令 | 配置位置 | 来源 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Python | 3 | `scripts/`、`schemas/`、`tests/` | 执行器、检查器、迁移和测试 | `py -m unittest` | Python 源文件与测试配置 | `repository_file`: `scripts/`、`tests/` | approved |
| Markdown | 任意 | `doc-atlas/`、`templates/`、`references/` | 人类可读知识与协议 | 由检查器验证 | Markdown 文件 | `repository_file`: `README.md` | approved |
| JSON Schema | 2020-12 及轻量 Schema | `schemas/` | 知识结构和状态约束 | `py scripts/check_knowledge_base.py` | `schemas/catalog.json` | `repository_file`: `schemas/README.md` | approved |

本节记录可由当前仓库定位的技术事实；大型目标项目内容过多时允许拆分技术基线文件，但必须由系统架构链接并保持相同语义。

## 版本权威

- Codex、Claude Code 和 Qoder 的插件清单由同一构建版本源生成，是 Context Atlas 产品版本的唯一权威。
- `knowledge-base.yaml` 是目标项目 `project_version`、`format_version` 和 `knowledge_revision` 的唯一权威。
- `created_by.product_version` 只提供生成追踪，不参与兼容判断。
- Schema 或协议变化只要影响持久知识表达，就提升 `format_version`；根清单不再维护独立 `protocol_version` 或 `schema_version`。
- 模板、兼容策略和执行器不得复制产品版本；构建器必须验证三个宿主插件清单的产品版本一致。

## 组件

1. **可安装 Skill**：作为 Agent 的薄执行适配层，只定义触发条件、意图边界、协议加载、流程编排和终止条件。正式知识维护拆分为 `context-atlas-add`、`context-atlas-revise` 和 `context-atlas-retire`，不保留通用 `context-atlas-update` 入口。
2. **插件执行协议**：`references/` 保存平台无关的完整执行规则，是知识采集、确认、冲突、状态转换和结果报告的唯一执行规范源。
3. **目标知识库协作说明**：随模板生成的 `05-知识治理/AI知识采集协议.md` 是持久化治理说明和无 Skill 时的最低兼容入口，不复制插件运行时细节。
4. **核心模板**：生成与语言无关的完整知识库。
5. **技术栈知识**：在同一知识库中记录各技术的版本、目录、用途、命令和配置。
6. **Schema**：作为文档结构和状态的唯一机器规范。
7. **检查器与执行器**：读取 Schema，实施确认门禁、受控写入和结构验证，不判断业务内容正确性。
8. **黄金样例**：验证单技术栈和多技术栈项目共享同一结构。
9. **数据资产**：记录重要业务数据的来源、负责人、质量、安全和保存规则，并引用数据库、接口契约和外部依赖等技术契约。
10. **需求、模块和接口知识**：需求与功能分别建模；模块、接口和可复用独立契约一项一文件，局部约束保留在所属知识文件中。
11. **插件资产构建器**：开发仓库只维护根目录唯一源码和 `assets/manifest.json`；构建器按白名单生成安装包的完整运行资产，开发仓库本身不是 Skill 运行目录。
12. **规格事实基线**：Context Atlas 保存当前批准且有效的需求、功能、架构、契约、约束、验收契约和证据关系，是开发者与 AI 读取项目事实的长期入口。
13. **变更工作区适配**：OpenSpec、Spec Kit、Issue 和其他任务系统描述单次变化、技术方案和执行任务；适配器默认只读，将其内容映射为来源、关系或知识 Proposal，不赋予外部状态正式批准权。
14. **规格审查能力**：规划一个只读 `context-atlas-review` Skill，检查清晰性、完整性、可测试性、冲突、断链和就绪度；它只输出候选结论，正式修改仍由 `add`、`revise` 或 `retire` 完成。

## 数据流

用户通过 Agent 发起请求。Agent 由 `add`、`revise` 或 `retire` Skill 进入对应维护流程，按 `references/` 中的执行协议检查项目和知识缺口，形成 Proposal 并向用户确认；确认后由共享执行器写入 `doc-<项目名>/`，再运行检查器。同一请求跨越新增、修订和退役时，Agent 必须生成一个原子复合 Proposal，由执行器统一实施，不能拆成可能留下半完成状态的独立写入。知识库中的协作说明保证产物可被独立理解，但不取代已安装插件的完整执行协议。知识库本身不调用模型，不提供独立用户 CLI。

版本数据流保持单向：构建版本源生成三个宿主插件清单；插件运行时读取目标 `format_version` 和兼容策略判断可读、可写或可转换状态；目标知识库独立维护业务项目版本和知识修订。产品版本差异本身不得直接判定知识库不兼容。

规格驱动开发采用三层数据流：Context Atlas 当前事实基线提供 `WHAT/WHY`、稳定设计契约和验收依据；变更工作区以 Proposal、规格 Delta、Design 和外部 Tasks 描述本次变化；Agent 与开发工具实现并产生测试和验收证据。变更验收后，外部归档动作只能发起基线合并候选，不能绕过 Context Atlas 的确认门禁。规格变化按 `ADDED`、`MODIFIED`、`REMOVED`、`RENAMED`、`SUPERSEDED` 表达；先实现 OpenSpec 适配，再实现 Spec Kit 适配。

## 权威边界

- 产品能力由功能基线定义，不以 Skill 描述代替需求。
- 知识采集的完整执行规则以 `references/` 为唯一规范源；Skill 必须引用它，不复制会独立漂移的规则。
- Proposal、确认、来源、冲突、影响、原子写入、回滚和验证由共享的 `references/`、`rules/`、`operations/`、`schemas/` 与执行器承担，不在三个维护 Skill 中重复实现。
- 目标知识库的协作说明只承载持久语义和最低兼容规则，不声明插件内部命令、运行时探测或平台适配细节。
- Schema 是机器结构权威；执行器和检查器不得维护可独立漂移的规则副本。
- 产品版本以宿主插件清单为唯一权威；知识库兼容性只由 `format_version` 与兼容策略决定。
- 模板、Schema、脚本、规则、操作定义和兼容策略各自只维护一份；插件 `assets/` 是构建产物，不是第二套源码。
- 自动化测试必须先构建插件，再从安装形态读取运行资产并验证行为。
- 仓库事实可以由 Agent 观察，但业务含义仍可能需要用户确认。
- AI 推测只能作为假设；用户确认后的知识才可成为批准基线。
- 检查通过只证明结构和追溯关系符合规则。
- 当前事实、变更设计、执行任务和验收证据分层保存；任务完成不得自动改写当前事实，验收证据通过也不得代替责任人确认。
- 规格质量门只决定信息是否足以进入设计、实现或验收，不决定外部任务是否获得执行许可。

## 产品边界

当已安装 Skill、插件协议和目标知识库说明之间出现差异时，先修正薄适配层和模板映射，不在多处扩展完整执行规则。Context Atlas 不定义项目如何开发；有保留价值的构建、测试和运行命令只作为技术栈或技术契约事实沉淀。
